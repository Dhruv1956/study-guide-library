1. The vacuum-cleaner puzzle

The lecture opens with a toy example that keeps coming back for the rest of this deck, so it's worth understanding really well.

Picture this

Imagine a tiny robot that lives in a house with just two rooms, room A and room B. The robot has one sensor: it can tell if the square it's currently standing on is dirty or clean. It has three possible moves: move left, move right, or suck up the dirt under it. That's it. That's the entire robot.

The lecture then asks a deceptively simple question: how would you program this robot to behave well? "Well" here just means: keep both rooms clean, without wasting moves.

This tiny example is used throughout the course because it's small enough to write out completely on one slide, yet it already contains every idea we need: sensing the world, choosing an action, and having some notion of "doing a good job."

Key takeaway

The big question this entire subject is trying to answer is: what does it actually mean for a machine to "act well"? Everything else — agents, rationality, search algorithms — is really just different ways of making that question precise and then answering it.

2. A short history of AI (1940s → today)

You don't need to memorise this timeline word-for-word, but it's genuinely useful context: it shows that "AI" has never been one fixed technique. It's a moving target — a name we give to whatever the current best approach for building rational agents happens to be.

DecadeWhat happened
1940sMcCulloch & Pitts built a mathematical model of a single brain cell (an artificial "neuron") in 1943. Alan Turing began thinking seriously about whether machines could "think."
1950sTuring proposed his famous Turing Test (1950) — if a human chatting with a hidden machine can't tell it's a machine, maybe we should call it intelligent. In 1956, at the Dartmouth Workshop, John McCarthy literally coined the term "Artificial Intelligence."
1960sELIZA, the first chatbot, appeared. Researchers built "General Problem Solver" style programs that searched for solutions step by step — the direct ancestor of Part 2 of this course.
1970sThe first "AI Winter." Computers were too weak and problems grew too fast (this "explosion" of possibilities is exactly what search algorithms in Part 2 are built to fight) — funding dried up.
1980s"Expert systems" (programs encoding a human expert's rules) revived funding. Hopfield networks (1982) and Boltzmann machines (1983, Geoffrey Hinton) laid early groundwork for neural networks.
1990sA second AI Winter. But quietly, probability-based methods (Bayesian networks, Hidden Markov Models) and reinforcement learning (TD-learning, TD-Gammon) matured. In 1997, IBM's Deep Blue beat world chess champion Garry Kasparov.
2000s"Big data" and much more powerful, cheaper computing hardware arrived.
2010sIBM Watson won at Jeopardy! (2011). AlexNet kick-started the deep learning boom (2012). Word2vec (2013). AlphaGo beat Go champion Lee Sedol (2016). The Transformer architecture ("Attention is all you need," 2017) — the technology behind every modern LLM — was introduced. GPT-1, BERT and GPT-2 followed.

AI is not one fixed technique — it's an evolving set of approaches to building agents that act rationally. Symbolic reasoning, search, probability, neural networks, and today's LLMs are all just different tools aimed at the same underlying question this course is about.

3. What is an "agent"?

Definition

An agent is anything that perceives its environment through sensors and acts upon that environment through actuators.

Let's slow down and unpack every word in that sentence, since it's the single most important definition in this whole part.

  • Environment — the world the agent lives in. For our robot, that's the two rooms.
  • Sensors — how the agent gets information in from the environment (this is called a percept). For our robot, that's the "is this square dirty?" sensor.
  • Actuators — how the agent pushes information/effects back out onto the environment (an action). For our robot, that's "move left," "move right," "suck."

So information flows in a loop: ENVIRONMENT → percepts → AGENT → actions → back to ENVIRONMENT, and this repeats forever.

Analogy

Think of you as an agent right now. Your environment is the room you're sitting in. Your sensors are your eyes and ears (percepts: what you see on this screen, what you hear around you). Your actuators are your hands and voice (actions: scrolling, typing, talking). A self-driving car works the same way — sensors are cameras/LIDAR, actuators are the steering wheel and pedals. A piece of software can be an agent too — its "sensors" might be reading keystrokes or files, and its "actuators" might be writing to a file or drawing something on screen.

Notice how general this definition is — it doesn't say anything about being "smart." A thermostat is technically an agent (sensor: temperature, actuator: turn heater on/off). Whether an agent behaves well is a completely separate question, which is exactly what "rational agents" (a bit later) is about.

4. Agent Function vs. Agent Program

This is a subtle distinction, but it's one of the more important ones in this deck, so let's take it very slowly with the vacuum robot as our running example.

Agent Function

A mapping from every possible sequence of percepts the agent could ever receive, to an action.

Think of it as an infinitely long lookup table: "if this is everything I've sensed so far, then do this action." It's a mathematical idea — it doesn't need to be something you could actually write down or run.

Agent Program

The actual, concrete piece of code that computes the agent function when you run it on real hardware.

This is the thing you actually write and execute. Every AI algorithm you'll ever learn is really just a different way of implementing some agent function.

Analogy

Think of a maths function like \( f(x) = x^2 \). The function is the abstract rule "square the input" — it exists whether or not anyone ever calculates it. A program that computes \(x^2\) in Python is one particular way of actually carrying that rule out. Same idea here: the agent function is the abstract "what should I do given what I've seen," and the agent program is the code that actually does it.

Worked example: the agent function for the two-room vacuum world

Here percepts look like [location, status], e.g. [A, Dirty] means "I am in room A and it is dirty." A full percept sequence is the entire history of everything sensed so far.

Percept sequenceAction
[A, Clean]Right
[A, Dirty]Suck
[B, Clean]Left
[B, Dirty]Suck
[A, Clean], [A, Clean]Right
[A, Clean], [A, Dirty]Suck
[A, Dirty], [B, Clean]Left
[A, Dirty], [B, Dirty]Suck
… (this table is infinite — one row for every possible history) …⋮

This table is the agent function — every conceivable history gets an action. But we obviously can't code up an infinitely long table. That's where the agent program comes in: a short piece of pseudocode that produces the same behaviour without needing to store every row.

Worked example: the agent program for the same robot

function REFLEX-VACUUM-AGENT([location, status]) returns an action
    if status = Dirty then return Suck
    else if location = A then return Right
    else if location = B then return Left

Notice this tiny 4-line program produces exactly the infinite table above, for every possible input. That's the whole point: a short program can compute a function that would take infinite space to write out explicitly.

Common confusion

Students often think "agent function" and "agent program" are just two names for the same thing. They're not: the function is the abstract "correct" input→output behaviour (it only cares about percept history → action, nothing about lookup tables or how it's computed). The program is one specific implementation of it. Many different programs (or algorithms) could compute the exact same agent function.

5. Rational agents

We now have vocabulary for "an agent" and "how it's implemented." But we still haven't answered the core question from slide 1: what does it mean for an agent to act well?

Definition

A rational agent is one that "does the right thing." More precisely: it's an agent that, at every step, selects the action expected to maximise its performance measure, given (a) the percepts it has seen so far, and (b) whatever built-in knowledge it starts with.

The new word here is performance measure — a score, decided by us (the designers), that tells us how good a whole sequence of actions turned out to be. For the vacuum robot, a performance measure might reward "amount of dirt cleaned" and penalise "electricity used" and "time taken."

Analogy

Think of a student writing an exam. "Rational" doesn't mean "always gets 100%" — it means, given what they've studied (their knowledge) and what's actually written on the paper (their percepts), they pick the answers that they expect will maximise their score (the performance measure). A rational agent can still be wrong if it's missing information — rationality is about making the best decision given what you know, not about being all-knowing.

Common confusion

"Rational" is not the same as "always successful" or "omniscient." A rational agent can still fail — for example, if a self-driving car's sensors simply can't see a pothole around a blind corner, swerving into it isn't irrational; the agent did the best it could with the percepts it had.

6. The PEAS framework

If we want to design a rational agent for some real task, we first need to precisely pin down the "task environment" it operates in. PEAS is a checklist for doing exactly that — four questions you answer for any agent you're designing.

LetterStands forQuestion it answers

Notice this is essentially the agent definition from earlier (Environment, Sensors, Actuators) plus one new piece — the Performance measure that turns "an agent" into a "rational agent" we can actually evaluate.

8. Classifying task environments

Once we know an agent's PEAS description, we can classify what kind of environment it's dealing with along six independent dimensions. This matters hugely in practice: harder categories on this list need much smarter (and often much more expensive) agents.

DimensionMeaning
Fully vs. Partially ObservableCan the agent's sensors see the complete state of the environment at every moment (fully), or only part of it (partially)?
Deterministic vs. Non-deterministicDoes the next state depend completely on the current state + the agent's action (deterministic), or can other unpredictable factors change the outcome (non-deterministic)?
Episodic vs. SequentialIs each decision independent of past/future decisions (episodic), or do earlier actions affect what happens later (sequential)?
Static vs. DynamicDoes the environment stay still while the agent is "thinking" (static), or can it change on its own in the meantime (dynamic)?
Discrete vs. ContinuousIs there a finite, countable set of states/actions (discrete), or an infinite continuum of possible values (continuous)?
Single-Agent vs. Multi-AgentIs our agent the only actor in the environment, or are there other agents (competing or cooperating) too?

Analogy — why these matter

Chess sounds "hard" but it's actually one of the friendlier categories here: you can see the whole board (fully observable), a move always has the exact same result (deterministic), and the board doesn't move while you think (static). A self-driving car is brutal by comparison: it can't see around corners (partial), other drivers behave unpredictably (non-deterministic), and the world keeps changing while it computes (dynamic). This is precisely why self-driving cars are a vastly harder engineering problem than a chess engine, even though "driving" feels easier to a human than "chess."

1. Formalising "finding a solution"

The deck opens with a very human question: you want to drive to a city you've never visited before (no map app, from scratch) — what do you actually need to know to solve this?

If you think about it for a moment, you need exactly five things:

  • Where you are now
  • Where you want to end up
  • What moves are available to you at each point
  • What each move costs you
  • How you'd recognise that you've arrived

That's it — that ordinary, everyday list of five things turns out to be exactly the formal definition of a search problem that computer scientists use. Nothing about it is arbitrary or "extra mathematical machinery" — it's just precise language for the obvious things you already need to know to solve any "get from here to there" problem.

2. The 5 parts of a search problem, made formal

Here is the same five-item list, now given formal names and notation. Read the "plain English" column first each time, then look at the formal notation next to it — don't let the symbols scare you, each one is just shorthand for the plain-English idea.

Formal nameNotationPlain English
State Space\(S\)The set of all possible situations ("states") the problem could ever be in.
Initial State\(s_0 \in S\)The one state where the agent actually starts.
Goal Statesa subset of \(S\)The state(s) that count as "done" / a solution.
Actions(s)\(S \to\) subsets of \(A\)Given a state \(s\), which actions (from the full set \(A\) of all actions) are actually available there?
Result(s, a)\(S \times A \to S\)The "transition model" — if you take action \(a\) in state \(s\), which state do you land in?
Action-Cost(s, a, s′)\(S \times A \times S \to \mathbb{R}\)The numeric price of taking action \(a\) in state \(s\) and arriving at \(s'\).
Key takeaway

Every single search problem you will ever see — no matter how exotic — is just these six pieces filled in differently. Once you can identify "what's my state space, what's my start, what's my goal, what actions do I have, what do they do, what do they cost" for any puzzle, you've fully formalised it.

4. State-space graphs

Definition

The State-Space Graph of a search problem is a graph where every node is a state, every edge is an action that takes you from one state to another, and every edge is labelled with its action's cost. (If moves are two-way, we just draw the edge as bidirectional.)

This is simply a way of drawing the six formal pieces from before: nodes = State Space, one special node = Initial State, some nodes highlighted = Goal States, edges = Actions/Result, edge labels = Action-Cost.

Worked example: the 2-room vacuum world as a graph

With 2 rooms, each Clean-or-Dirty, and the robot in one of the 2 rooms, there are \(2 \times 2 \times 2 = 8\) possible states in total. Here's a small piece of that graph to build intuition, showing just one room's worth of "Suck" and "Move" edges:

The full graph repeats this pattern across all 8 states. Two patterns to notice, because they show up on the original slide's diagram:

  • Every "real" move costs 1 — sucking dirt that's actually there, or moving to the other room.
  • Every "wasted" move costs 2 and loops back to the same state — e.g. trying to move further left when you're already in the leftmost room, or trying to suck a room that's already clean. Charging more for these self-loops is exactly the "better Action-Cost function" idea from the previous section — it nudges the agent away from pointless actions.

5. Best-First Search — the master algorithm

Here's the single most important idea in this whole deck: almost every search algorithm you'll learn (BFS, DFS, Uniform-Cost Search, Greedy Search, A*) is actually the exact same algorithm, called Best-First Search, with just one small ingredient swapped out each time.

Best-First Search keeps two pieces of bookkeeping:

  • A frontier — the "waiting room" of states we know about but haven't explored yet, kept sorted by how promising they look.
  • A reached table — the cheapest known path found so far to each state we've seen.

"How promising a state looks" is measured by an evaluation function \(f(n)\). Whichever node currently has the smallest \(f(n)\) is judged "best," and gets explored (expanded) next.

Best-First Search — the general algorithm
1. Frontier ← priority queue containing only the initial state, ordered by f(n)
2. Reached  ← table recording the cheapest known path to each state so far
3. if Frontier is empty then return failure
4. Remove the node with the lowest f(n) from Frontier  ← this is the "best" node
5. if that node is a goal state then return the solution
6. for each child of that node:
       if unseen OR reached with a smaller f(n) than before:
           update Reached and Frontier
7. Repeat from step 3
Key takeaway

Memorise this skeleton once, and every algorithm coming up (UCS, BFS, DFS, Greedy, A*) is just "Best-First Search, but with this particular \(f(n)\)." You'll see the exact table of substitutions in section 8 below.

6. State space vs. search tree — a distinction worth pausing on

State Space / State-Space GraphSearch Tree
A fixed mathematical object — the graph of all states and the actions connecting them. It does not change as the algorithm runs.What the algorithm builds while it explores. The same state can appear more than once in the tree, reached via different paths.
Analogy

The state-space graph is like the map of a whole city — it exists whether or not you ever visit it. The search tree is like the specific trail of footprints you personally leave as you explore that city, turn by turn — including any dead ends you doubled back from. Two different routes might both pass through the same intersection (state), so that intersection shows up as two different nodes in your trail (tree), even though it's only one place on the map (graph).

8. Tracing Uniform-Cost Search, step by step

Here \(f(n) = g(n)\) — the total path cost travelled so far to reach node \(n\). At each step we pop the cheapest-so-far node from the frontier, and expand it (look at its neighbours).

Analogy

Result

UCS returns the path A → H → I → K → M (Arad → Sibiu → Râmnicu Vâlcea → Pitești → Bucharest), with total cost \(140 + 80 + 97 + 101 = \mathbf{418}\) km. Notice this path is not the one that pops up early (like A→D→...) — UCS patiently keeps exploring cheaper branches first, which is exactly what guarantees it finds the truly cheapest path.

Common confusion

Notice step ⑩: when we expand K, we discover a cheaper way to reach M (418, via K) than the one we already knew about (450, via L). UCS doesn't just ignore this — it updates M's entry in the frontier to the cheaper value. This "update if we find something cheaper" rule (step 6 of the algorithm) is exactly what guarantees UCS always finds the optimal path.

9. Turning UCS into BFS / DFS (efficiency tweaks)

Since BFS and DFS are just special cases of Best-First Search (from section 7's table), a couple of small implementation shortcuts become possible:

When f(n) = depth(n) — the BFS case
  • Use a plain FIFO queue for the frontier instead of a full priority queue (much cheaper).
  • You can goal-test a node the moment it's generated, not only once it's popped — because no state will ever be revisited at a smaller depth later.
  • The "reached with a smaller f(n)" check in step 6 can be dropped entirely — it can never actually trigger.
When f(n) = −depth(n) — the DFS case
  • Use a LIFO stack for the frontier instead of a priority queue.

10. Heuristic functions — giving search a sense of direction

UCS, BFS and DFS are called uninformed (blind) searches — they have absolutely no sense of which unexplored node is "closer" to the goal; they only know what they've already paid to get somewhere. As the state space grows, exploring blindly becomes far too slow to be practical. The natural next idea: what if the search could estimate how promising a state looks, before even expanding it?

Definition

A heuristic function \(h(n)\) is an estimate of the cost from node \(n\) to the nearest goal. By definition \(h(\text{goal}) = 0\). It's problem-specific — you build it using whatever domain knowledge you have about the problem.

  • Route-finding: \(h(n)\) = straight-line ("as the crow flies") distance from city \(n\) to the destination.
  • 8-Puzzle: \(h(n)\) = number of tiles that are currently in the wrong position.

13. Admissible heuristics

A* found the optimal path in our example above — but was that just luck, or does A* always find the optimal path? The answer: only if the heuristic satisfies one particular property.

Definition

A heuristic \(h\) is admissible if, for every node \(n\): \[ h(n) \le p(n) \] where \(p(n)\) is the true optimal cost from \(n\) to the goal. In plain English: an admissible heuristic never overestimates — it might guess too low, but it can never promise a shorter remaining trip than what's actually possible.

Analogy

Straight-line ("as the crow flies") distance is a perfect example of an admissible heuristic for driving distance — flying straight over hills and rivers can never be longer than actually driving the winding roads between two points. It might be a big underestimate, but it will never lie in the "overestimate" direction.

Key result (why we care)

If the heuristic \(h\) is admissible, then A* is guaranteed to return an optimal solution. This is the entire reason admissibility matters.

▸ Show the full formal proof (optional — for when you want the rigor)

Setup: Let \(C^*\) be the true optimal cost from the initial state to the goal, achieved by the optimal path \( \text{Initial}=n_0 \to n_1 \to \cdots \to n_k = \text{Goal} \).

Proof by contradiction: Suppose instead A* returns some non-optimal path \( \text{Initial}=n_0 \to n_1' \to \cdots \to n_l'=\text{Goal} \) with cost \(C > C^*\).

Since the optimal path exists but A* didn't return it, there must be some node \(n_i\) (with \(1 \le i \le k-1\)) on the optimal path that got generated but never expanded by A*. Why must such a node exist? Because A* returned a goal via a different, worse path — so somewhere along the true optimal path, A* stopped pursuing it.

Because \(n_l'\) (the goal on the returned path) was popped from the frontier with \(f(n_l') = C\), and A* always pops the smallest \(f\)-value available, every node still sitting in the frontier — including our \(n_i\) — must satisfy \(f(n_i) > C\). Since \(C > C^*\), this gives us \(f(n_i) > C^*\).

But now compute \(f(n_i)\) directly:

\[ f(n_i) = g(n_i) + h(n_i) \]

Since \(n_i\) lies on the optimal path, \(g(n_i) = g^*(n_i)\) (its cost-so-far already equals the true optimal cost to reach it). And because \(h\) is admissible, \(h(n_i) \le p(n_i)\) (the true remaining cost from \(n_i\)). So:

\[ f(n_i) = g^*(n_i) + h(n_i) \le g^*(n_i) + p(n_i) = C^* \]

So we've shown \(f(n_i) \le C^*\) — but two paragraphs ago we showed \(f(n_i) > C^*\). Contradiction. So our assumption was wrong: A* cannot return a non-optimal path when \(h\) is admissible. \(\blacksquare\)

14. Consistent heuristics

Admissibility guarantees A* finds the optimal answer, but proving a heuristic is admissible (comparing against the "true" cost) can be awkward. There's a second, stronger, easier-to-check property called consistency.

Definition

A heuristic \(h\) is consistent if, for every node \(n\) and every successor \(n'\) reached via action \(a\): \[ h(n) \le c(n,a,n') + h(n') \]

This is exactly the triangle inequality you already know from geometry — "going directly can never be longer than going via a detour." Here, "going directly" is estimating from \(n\), and "going via a detour" is stepping to \(n'\) first (paying the real cost \(c\)) and then estimating the rest from there.

Key result

If \(h\) is consistent, then \(h\) is admissible (proof below) — and we already know admissible ⟹ A* is optimal. So put together: if a heuristic is consistent, A* is guaranteed to find the optimal solution. This is the version of the result you'll use most often in practice, because consistency is usually easier to verify.

▸ Show the full formal proof that consistent ⟹ admissible (optional)

We prove \(h(n) \le p(n)\) for every node \(n\), by induction on \(k\), the number of intermediate nodes on the cost-optimal path from \(n\) to the goal \(g\).

Trivial case: if there's no path at all from \(n\) to \(g\), then \(p(n)=\infty\), so \(h(n)\le p(n)\) holds automatically.

Base case (\(k=0\)): the goal \(g\) is a direct successor of \(n\). By consistency, \(h(n) \le c(n,g) + h(g)\). Since \(c(n,g)=p(n)\) (there are no intermediate nodes) and \(h(g)=0\) by definition, we get \(h(n) \le p(n)\).

Inductive step: assume the claim holds for any node whose optimal path to the goal has \(k-1\) intermediate nodes. Let \(n\) be a node whose optimal path has \(k\) intermediate nodes: \(n \to a_1 \to a_2 \to \cdots \to a_k \to g\). By consistency, \(h(n) \le c(n,a_1) + h(a_1)\). By the induction hypothesis applied to \(a_1\) (which has \(k-1\) intermediate nodes to go), \(h(a_1) \le p(a_1)\). Combining: \(h(n) \le c(n,a_1) + p(a_1) = p(n)\) (since the whole path is cost-optimal). This completes the induction, so \(h(n) \le p(n)\) for every node, i.e. \(h\) is admissible. \(\blacksquare\)

Admissible does not always mean consistent

These two properties are related but not identical — admissibility is the weaker (more easily satisfied) condition. Here's the slide's counter-example:

Why is the N-Queens heuristic not admissible?

Recall: admissible means "never overestimates the true remaining cost." In N-Queens, one single move (relocating one queen) can sometimes remove several attacking pairs at once, so the heuristic can be larger than the number of moves actually still needed — it can overestimate. That single possibility is enough to break admissibility (and this is exactly why this heuristic shows up again in Part 3, for local search rather than for A*, where the admissibility guarantee isn't needed).

Key takeaway for all of Part 2

Every algorithm in this deck — BFS, DFS, UCS, Greedy, A* — is the same seven-line Best-First Search skeleton with one number, \(f(n)\), swapped out. UCS is always optimal but explores blindly. Greedy is fast but can be fooled. A* combines both ideas and is fast and optimal, as long as its heuristic is admissible (or, more strongly, consistent).

Part 2 was all about finding the best path from start to goal. Part 3 asks: what if you don't care about the path at all — only about ending up in a good final configuration? That question leads to a completely different family of algorithms.

Analogy

Slides 2–4

2. Why use local search, and the "landscape" picture

Local search is useful when:

  • The problem only cares about the final configuration, not the path — e.g. job scheduling, robot path planning itself, hyperparameter tuning, circuit design, the Travelling Salesman Problem, puzzles like 8-Queens.
  • You have huge or even infinite state spaces where systematic search (Part 2's algorithms) would be far too slow or memory-hungry.
  • You want something that uses very little memory — just the current state (and maybe a couple of others).
The trade-off

Local search usually does not explore the state space completely, and so it may not return the true best (optimal) solution. In exchange, it's often much faster and more practical than exhaustive search.

Visualising local search: the state-space landscape

Picture every possible state as a single point on a landscape:

  • Location on the landscape = the state.
  • Elevation at that point = the value of an objective/heuristic function there.

Elevation can point two ways, depending on what we're optimising:

  • Objective function (to be maximised) → higher is better → think of climbing toward peaks.
  • Heuristic/cost function (to be minimised) → lower is better → think of descending into valleys.

The goal of local search is simply: find the highest peak (or lowest valley) — the global maximum (or minimum) — by repeatedly moving to better neighbouring states.

3. Hill Climbing (Greedy Local Search)

The simplest possible local search algorithm: from the current state, look at all neighbouring states, and move to whichever neighbour is best. Stop once no neighbour is better than where you already are.

function HILL-CLIMBING(problem) returns a state that is a local maximum
    current ← Initial state
    while true do:
        neighbour ← the highest-valued successor state of current
        if VALUE(neighbour) ≤ VALUE(current) then return current
        current ← neighbour

"Value" here means the objective function — higher is better, so we're climbing uphill. (If you're minimising a cost/heuristic instead, just flip every comparison.)

4. Hill Climbing on the 8-Queens problem

The 8-Queens problem: place 8 queens on an 8×8 chessboard so that no two queens attack each other (no two share a row, column, or diagonal). Let's set up the local-search version of this problem, piece by piece.

  • State space: every arrangement with exactly one queen per column — that's \(8^8 = 16{,}777{,}216\) possible states.
  • Successors of a state \(n\): all states reachable by moving a single queen to a different row within its own column. Since each column has 7 other rows to move to, every state has \(7 \times 8 = 56\) successors.
  • Heuristic \(h(n)\) = number of pairs of queens that attack each other (directly or diagonally). A perfect solution has \(h(n)=0\).
  • Objective function = \(-h(n)\) (the negative of the heuristic). Maximising this objective is the same as minimising \(h(n)\) — the fewer attacking pairs, the better.

But every neighbouring state is worse, so hill climbing has no way to see that a true solution might be just a few more moves away, past this dip. This is called a local maximum (in objective-function terms) or local minimum (in heuristic terms) — a state that looks like the best option locally, but isn't the best option globally.

Slide 12

5. Why hill climbing gets stuck

The worked example above wasn't a one-off unlucky run — it demonstrates hill climbing's fundamental weakness:

  • Hill climbing only ever moves to a strictly better neighbour — it never accepts a move that makes things (even slightly) worse.
  • Because of this "greedy," never-look-back behaviour, it can easily get trapped in local optima (a bump that's locally the best, but not globally the best) or on plateaus (flat regions where no neighbour is strictly better, so it can't tell which way to go).
Key takeaway

Once hill climbing gets stuck, it has no way to escape — it simply stops. Everything in the rest of Part 3 (Simulated Annealing, Evolutionary Algorithms) exists specifically to fix this one weakness.

6. Simulated Annealing

The key idea: what if, instead of always rejecting a worse move, we sometimes allowed one? Occasionally accepting a "downhill" move gives the search a chance to walk through a local optimum or plateau, instead of getting permanently stuck there.

But how often should we accept a worse move?

  • Too often → the search behaves like a random walk and never settles down anywhere.
  • Too rarely → it behaves just like plain hill climbing, and gets stuck just the same.

Simulated annealing's balance: accept worse moves more freely early on, and less freely as time goes on. This is controlled by a gradually decreasing temperature parameter, \(T\).

Analogy — where the name comes from

This is directly inspired by annealing in metallurgy — slowly cooling a hot metal lets its atoms settle into a strong, stable, low-energy structure, whereas cooling it too fast traps it in a weak, disordered state. Here, "hot" = the search is free to explore widely and jump around (even into worse states); "cooling down" = the search gradually becomes stricter and settles into a good state.

function SIMULATED-ANNEALING(problem) returns a solution state
    current ← Initial state
    for t = 1 to ∞ do:
        T ← schedule(t)                          // T decreases over time
        if T = 0 then return current
        next ← a randomly chosen successor of current
        if VALUE(next) > VALUE(current) then
            current ← next                       // always take an uphill move
        else
            ΔE ← VALUE(current) − VALUE(next)     // how much worse is "next"?
            prob ← e^(−ΔE / T)
            if random() < prob then current ← next   // sometimes take it anyway

schedule(t) is any function that decreases over time \(t\). random() returns a random number in \([0,1)\).

Making sense of the probability formula

The heart of the algorithm is \( \text{prob} = e^{-\Delta E/T} \). Let's build intuition for it by checking three extreme cases:

As...prob →In plain English
\(\Delta E \to 0\) (a tiny downhill step)\(1\)Small worsening moves are almost always accepted — barely worse, and worth risking to escape a shallow dip.
\(\Delta E \to \infty\) (a huge downhill step)\(0\)Big worsening moves are almost never accepted — jumping to a much worse state is rarely worth it.
\(T \to 0\) (late in the run)\(0\)As the "temperature" cools, the algorithm becomes increasingly reluctant to accept any downhill move — it gradually turns into plain hill climbing.
Key takeaway

Early on (\(T\) high) we explore freely; later on (\(T\) low) we settle down and exploit what we've found. This is the famous exploration–exploitation trade-off that shows up throughout AI, not just here.

One practical tweak the slide mentions: if you already know the best possible value of the objective function in advance, you can simply stop the moment you reach it, instead of running through all remaining iterations.

8. From a single state to a whole population

Simulated annealing improved on hill climbing, but it still keeps track of only one candidate state at a time. Even with tricks like random restarts, a single-solution search can still end up stuck exploring just one region of a huge landscape.

The next idea

What if, instead of one state, we searched with a whole population of states, all at once, in parallel?

  • A diverse population gives much broader coverage of the search space.
  • Good "sub-solutions" discovered in one state could potentially be combined with good sub-solutions from a completely different state.

This is the core idea behind Evolutionary Algorithms: borrowing the mechanics of biological evolution — variation and selection — and using them for optimisation.

10. Evolutionary algorithms, piece by piece

Definition

An evolutionary algorithm is a population-based, stochastic optimisation/search method inspired by natural selection.

The core loop (repeated once per "generation")

  1. Initialise a population of candidate solutions (states).
  2. Evaluate the fitness of every state in the population.
  3. Select the fitter candidates to reproduce.
  4. Apply variation operators (recombination/crossover, mutation) to produce offspring.
  5. Form the next generation from these offspring.

This loop repeats until some stopping criterion is met. With a reasonably large initial population (at least 100–200 for medium-difficulty problems) run over many generations (typically 500–1000), the process tries to ensure "survival of the fittest," gradually driving the population toward better solutions.

Key components you need to define

ComponentWhat it means
RepresentationHow you encode a candidate solution/state — a string, a real-valued vector, a tree, etc.
Fitness functionA function measuring how good a solution is (e.g. the negative of a heuristic function, so "lower heuristic" becomes "higher fitness").
Selection mechanismHow you decide which individuals get to reproduce — common choices are Weighted-Random-Choices (a.k.a. Roulette Wheel Selection) and Tournament Selection.
Variation operatorsCrossover/Recombination (mixing two parents) and Mutation (small random tweaks).

That single change is what turns "search" into "game-playing," and it's the subject of this final part.

Slides 1–3

1. Multi-Agent Decision Making, and Zero-Sum Games

Why games need a new kind of search

Many decision-making problems involve multiple intelligent agents with conflicting objectives. Unlike classical search problems, where the environment is passive, game-playing problems require an agent to consider the actions of an opponent. The success of a move depends not only on the agent's own decision, but also on how other players respond. Games provide a convenient framework for studying strategic reasoning, because their rules, states, and possible actions are usually well defined. Popular examples studied in AI include Tic-Tac-Toe, Chess, Checkers, and Go.

Definition — Two-Player Zero-Sum Games

Two-player zero-sum games are games with two players who take turns and play against each other, where what is good for one player is equally bad for the other. Examples: Tic-Tac-Toe, Chess.

A naming subtlety worth knowing

In a general two-player zero-sum game, the sum of the payoffs to both players is constant for all possible outcomes — more precisely, these are constant-sum games. The term "zero-sum" is used anyway, because it's always possible to redefine the payoffs so that the sum is zero, without changing the strategic structure of the game at all.

The formal definition of a game

A game, as seven precise pieces

A game can be defined with the following components:

  • \(S\) — the set of states; \(P\) — the set of players; \(A\) — the set of actions. For a two-player zero-sum game, \(P=\{\text{MAX},\text{MIN}\}\), where MAX is the player who plays first.
  • \(s_0\) — the initial state, specifying how the game is set up at the start.
  • To-Move(\(s\)) — a function from \(S\) to \(P\): whose turn it is to move in state \(s\).
  • Actions(\(s\)) — the set of legal moves in state \(s\), a subset of \(A\).
  • Result(\(s,a\)) — a function from \(S\times A\) to \(S\): the transition model, defining the state that results from taking action \(a\) in state \(s\).
  • Is-Terminal(\(s\)) — a terminal test, true when the game is over. States where the game has ended are called terminal states.
  • Utility(\(s,p\)) — a function from \(S\times P\) to \(\mathbb{R}\) (also called an objective or payoff function): the final numeric value to player \(p\) when the game ends in terminal state \(s\).
Key takeaway — this is the same skeleton as Part 2, with one new piece

Compare this to a Part 2 search problem: states, actions, a transition model, and a goal/terminal test are all exactly the same idea. The genuinely new ingredients are To-Move(\(s\)) (because now more than one agent takes turns acting) and Utility replacing a single "cost" (because now two players disagree about what's good). Everything built in this part is really just Part 2's search machinery, adapted for an opponent.

2. Optimal Decisions: The Minimax Value

Definition

Given a game, the optimal strategy can be determined using the minimax value of each state \(s\), denoted \(\text{Minimax}(s)\). It is the utility of being in state \(s\) for MAX, assuming that both players play optimally from there to the end of the game.

The intuition, in plain words

MAX wants the biggest possible outcome; MIN wants the smallest possible outcome (for MAX — which, since it's zero-sum, is the same as MIN wanting the biggest outcome for itself). So when it's MAX's turn to move, MAX will pick whichever next state has the highest minimax value. When it's MIN's turn, MIN will pick whichever next state has the lowest minimax value. "Minimax" is just this tug-of-war, computed all the way down the tree.

The recursive definition

For a terminal state \(s\): \(\text{Minimax}(s)=\text{Utility}(s,\text{MAX})\).

For a non-terminal state: MAX prefers to move to a state of maximum value when it's MAX's turn; MIN prefers to move to a state of minimum value when it's MIN's turn. (Minimum value for MAX is equivalent to maximum value for MIN.) So:

\[ \text{Minimax}(s) = \begin{cases}\text{Utility}(s,\text{MAX}) & \text{if } s \text{ is terminal}\\[4pt] \displaystyle\max_{a\in\text{Actions}(s)}\text{Minimax}(\text{Result}(s,a)) & \text{if To-Move}(s)=\text{MAX}\\[8pt] \displaystyle\min_{a\in\text{Actions}(s)}\text{Minimax}(\text{Result}(s,a)) & \text{if To-Move}(s)=\text{MIN}\end{cases} \]

How to actually use this to pick a move

At a state \(s\), the best action is the one that leads to a state of: maximum Minimax value among all successor states, if To-Move(\(s\))=MAX; or minimum Minimax value, if To-Move(\(s\))=MIN.

Note that the computation of the minimax value of a state \(s\) starts at terminal states and works backward all the way to state \(s\) — you can only know if a move is good by first knowing how the game plays out after it.

The Minimax Search algorithm

Pseudocode — MINIMAX-SEARCH 
function MINIMAX-SEARCH(state) returns an action
    player ← TO-MOVE(state)
    value, move ← MAX-VALUE(state)
    return move

function MAX-VALUE(state) returns a (utility, move) pair
    if IS-TERMINAL(state) then return UTILITY(state, player), null
    v ← −∞
    for each a in ACTIONS(state) do
        v′, a′ ← MIN-VALUE(RESULT(state, a))
        if v′ > v then v, move ← v′, a
    return v, move

function MIN-VALUE(state) returns a (utility, move) pair
    if IS-TERMINAL(state) then return UTILITY(state, player), null
    v ← +∞
    for each a in ACTIONS(state) do
        v′, a′ ← MAX-VALUE(RESULT(state, a))
        if v′ < v then v, move ← v′, a
    return v, move

Notice MAX-VALUE and MIN-VALUE call each other, recursively — exactly mirroring the definition above: to evaluate a MAX state, ask MIN-VALUE about each successor; to evaluate a MIN state, ask MAX-VALUE about each successor. The recursion bottoms out at IS-TERMINAL, where the true utility is simply read off.

4. Why Plain Minimax Isn't Enough

The Minimax Search algorithm's cost

Minimax Search performs a depth-first search of the game tree, starting from the node corresponding to the input state. If there are \(b\) legal moves from each node and the maximum depth of the tree is \(m\), the time complexity of minimax-search is \(O(b^m)\) — exponential in the depth of the tree.

Why this actually matters — chess as a worked-out example

The exponential time complexity makes minimax-search practically infeasible for complex games. The game tree for chess has an average branching factor of about \(b=35\) and an average depth of about \(m=80\). So the total number of states in an average game tree is about \(35^{80}\approx10^{123}\) — nowhere close to feasible to search, on any computer that could ever be built.

Key takeaway

Minimax is correct — it always finds the true optimal move — but it's useless in practice for any game complex enough to be interesting. The rest of this part is entirely about fixing this, first exactly (Alpha-Beta pruning) and then approximately (heuristic techniques).

5. Alpha-Beta Pruning

The key question

Can we find the minimax values in a cleverer way? Yes — by skipping the nodes that are irrelevant to the minimax value of the input state. This is known as alpha-beta pruning of the game tree. The ALPHA-BETA-SEARCH algorithm is the improvement over MINIMAX-SEARCH obtained by incorporating this pruning.

Pseudocode — ALPHA-BETA-SEARCH 
function ALPHA-BETA-SEARCH(state) returns an action
    player ← TO-MOVE(state)
    value, move ← MAX-VALUE(state, −∞, +∞)
    return move

function MAX-VALUE(state, α, β) returns a (utility, move) pair
    if IS-TERMINAL(state) then return UTILITY(state, player), null
    v ← −∞
    for each a in ACTIONS(state) do
        v′, a′ ← MIN-VALUE(RESULT(state, a), α, β)
        if v′ > v then
            v, move ← v′, a
            α ← max{α, v}
        if v ≥ β then return v, move
    return v, move

function MIN-VALUE(state, α, β) returns a (utility, move) pair
    if IS-TERMINAL(state) then return UTILITY(state, player), null
    v ← +∞
    for each a in ACTIONS(state) do
        v′, a′ ← MAX-VALUE(RESULT(state, a), α, β)
        if v′ < v then
            v, move ← v′, a
            β ← min{β, v}
        if v ≤ α then return v, move
    return v, move
What α and β actually mean
  • \(\alpha\) — the value of the best (highest-value) choice found so far for MAX, anywhere along the current path from the root.
  • \(\beta\) — the value of the best (lowest-value) choice found so far for MIN, anywhere along the current path from the root.

Both start as wide open as possible (\(\alpha=-\infty\), \(\beta=+\infty\)) and only ever tighten as the search proceeds. The pruning trigger is simple: inside MAX-VALUE, once \(v\ge\beta\), MAX already has a move at least as good as something MIN can force earlier in the tree — so MIN would never let the game reach this node, and there's no point computing the rest of its siblings. The mirror-image logic applies inside MIN-VALUE when \(v\le\alpha\).

In plain MINIMAX-SEARCH, every intermediate call to MAX-VALUE/MIN-VALUE returns the true minimax value of its subtree. In ALPHA-BETA-SEARCH, this is not guaranteed — an intermediate call's returned value is only a bound on the true minimax value, provably good enough for the decision at the parent state (exactly what happened with C above: its "true" value of 2 was never fully double-checked against T5/T6, but it didn't need to be). ALPHA-BETA-SEARCH guarantees the correct best move only at the root — but that guarantee is all that's actually needed. The whole point of alpha-beta-search is to get the same answer as minimax-search, with less work.

7. Move Ordering — When Does Alpha-Beta Help the Most?

The effectiveness of pruning depends entirely on move order

The effectiveness of alpha-beta pruning is highly dependent on the order in which the child states of any node are examined. With "perfect" ordering of moves at every state, alpha-beta-search needs only \(O(b^{m/2})\) nodes, instead of \(O(b^m)\) for minimax-search. This means the effective branching factor reduces from \(b\) to \(\sqrt b\).

What this means for chess, concretely

For chess (\(b\approx35\)), perfect move ordering means an effective branching factor of about \(\sqrt{35}\approx6\) — instead of 35. That's the difference between a hopeless \(35^{80}\) and a merely enormous \(6^{80}\); still not fully solvable, but a genuinely dramatic improvement, and exactly why every real game-playing program invests heavily in good move ordering.

8. Beyond Alpha-Beta — What Real Game Engines Actually Do

Even perfect ordering isn't enough for chess

Even an alpha-beta-search with better move ordering is not feasible for games like chess, because there are still too many states to explore in the available time.

Shannon's two strategies (1950) — the original idea

In the first paper on computer game-playing, Programming a Computer for Playing Chess (C. E. Shannon, Philosophical Magazine, Vol. 41, 7th series, 256–275, 1950), Claude Shannon recognized this exact problem and proposed two strategies:

  • Type A strategy — considers all possible moves to a certain depth in the search tree, then uses a heuristic function to estimate the utility of states at that depth. Explores a wide but shallow portion of the tree.
  • Type B strategy — ignores moves that look bad, and follows promising paths "as far as possible." Explores a deep but narrow portion of the tree.
Key ideas used in practice — heuristic alpha-beta search
  • Cutoff test replacing terminal test — stop at a depth limit instead of searching all the way to the end of the game (this is Type A in action).
  • Evaluation function replacing utility function — estimate how good a non-terminal position is (e.g. king safety, piece mobility, in chess) instead of computing the true game value.
  • Move ordering — searching the most promising moves first (e.g. using prior knowledge or iterative deepening results) makes alpha-beta pruning far more effective, potentially reducing the effective branching factor dramatically — exactly Section 7's \(O(b^{m/2})\) result, chased deliberately.
  • Transposition tables — caching previously-seen positions (since different move orders can reach the same position) avoids redundant search.
  • Forward pruning / selective search — deliberately ignoring moves that look bad, at the risk of missing something (this is Type B; used carefully, since it's not guaranteed safe, unlike alpha-beta's pruning).
  • Iterative deepening — run depth-limited search with increasing depth; useful for time management, and for improving move ordering at each successive depth.
And beyond alpha-beta entirely — where modern game AI has gone
  • Monte Carlo Tree Search (MCTS) — used in modern game AI (e.g. Go, and hybrid approaches in chess engines). Builds a search tree using random/guided playouts, rather than exhaustively expanding every node.
  • Learned evaluation functions — systems such as AlphaZero use deep neural networks, trained through self-play/reinforcement learning, to learn an evaluation function — combined with MCTS to evaluate board positions and select the most promising moves.
Key takeaway for all of Part 4 — and the whole course

The story of this entire part mirrors the story of Part 2 almost exactly: start with a method that's provably correct but exponentially slow (Minimax, like uninformed search); find a way to get the exact same answer with much less work by being smarter about what to explore (Alpha-Beta pruning, like A*'s use of a heuristic); and when even that isn't fast enough for the hardest real-world cases, fall back on principled approximations (heuristic evaluation functions and depth cutoffs, echoing Part 3's local search trade-off of optimality for speed). Whether the environment is passive (Parts 2–3) or adversarial (Part 4), the same core tension — correctness versus computational feasibility — keeps reappearing, and the same family of ideas (heuristics, pruning, approximation) keeps being the answer.

Constraint Satisfaction Problems

Every search problem in Part 2 asked "what sequence of actions reaches a goal?" This part asks a subtly different question: forget the path entirely — what assignment of values satisfies every rule at once? That reframing is what makes Constraint Satisfaction Problems (CSPs) different from ordinary search, and it turns out to be exactly the right lens for scheduling, puzzles, and map colouring alike.

Slides 1–2

1. Why CSPs? Three Motivating Examples

The common thread

Many problems require us to make a collection of decisions while respecting certain restrictions (constraints). Three common examples:

  1. Map Colouring — given a map, assign colours to regions such that neighbouring regions get different colours.
  2. Exam Scheduling — given a set of courses (students may be enrolled in multiple) and a set of time slots, schedule exams so no student has two exams at the same time.
  3. Sudoku — given a partially filled 9×9 grid, assign numbers to the remaining cells so every row, column, and 3×3 subgrid contains 1–9 exactly once.

Notice what all three have in common: there's no notion of "moving through" a sequence of states one action at a time. There's just a set of unknowns, and a set of rules those unknowns must jointly satisfy.

Formalising a CSP

Definition — the three components of a CSP
  • Set of variables: \(\{X_1,X_2,\dots,X_n\}\)
  • Domains of the variables: for each \(1\le i\le n\), the set \(D_i\) is the set of possible values of \(X_i\).
  • Constraints: specify the allowable combinations of values.
Definition — assignments
  • An assignment of values to only some of the variables is a partial assignment.
  • An assignment of values to all of the variables is a complete assignment.
  • An assignment that does not violate any constraints is a consistent assignment.
  • A solution to the CSP is a complete and consistent assignment.
Key takeaway — this is a strictly smaller vocabulary than Part 2's search problems

There's no transition model, no path cost, no notion of one state being "reached from" another. A CSP only has three ingredients: variables, domains, constraints. Everything in this part — every algorithm, every worked example — is really just different strategies for building up a complete, consistent assignment out of these three ingredients.

Example 1 — Map Colouring

Problem

Variables: \(A,B,C,D,E,F,G\)

Constraints:

  • \(c_{ij}=m_{ij}\) for every cell already filled with a given value \(m_{ij}\);
  • \(c_{ij}\ne c_{ik}\) for all \(j\ne k\) — no repeats within a row;
  • \(c_{ij}\ne c_{kj}\) for all \(i\ne k\) — no repeats within a column;
  • \(c_{ij}\ne c_{kl}\) whenever \((i,j)\ne(k,l)\) and both cells lie in the same \(3\times3\) subgrid (i.e. \(i,k\) and \(j,l\) both fall in the same block among \(A=\{1,2,3\}\), \(B=\{4,5,6\}\), \(C=\{7,8,9\}\)) — no repeats within a subgrid.

Any correct solution to the Sudoku is a solution to this CSP.

3. Backtracking Search

Pseudocode — BACKTRACKING-SEARCH 
function BACKTRACKING-SEARCH(csp) returns a solution or failure
    return BACKTRACK(csp, {})

function BACKTRACK(csp, assignment) returns a solution or failure
    if assignment is complete then return assignment
    var ← SELECT-UNASSIGNED-VARIABLE(csp, assignment)
    for each value in ORDER-DOMAIN-VALUES(csp, var, assignment) do
        if value is consistent with assignment then
            add {var = value} to assignment
            result ← BACKTRACK(csp, assignment)
            if result ≠ failure then return result
            remove {var = value} from assignment
    return failure

Backtracking search is a recursive depth-first search performed on the search tree of partial assignments — try a value, recurse; if that whole branch fails, undo the assignment ("backtrack") and try the next value.

Worked example — a small map colouring CSP

Key takeaway — plain backtracking can be genuinely wasteful

Notice how much work happened before the algorithm realised the assignment for \(A\) had to be changed — it tried every combination of B and C under \(A=r\) (all doomed to fail once D is reached) before finally backtracking all the way back to \(A\). In fact, the value \(r\) could have been removed from \(D_A\) before search even began: since \(D_D=\{r\}\) and the constraint \(A\ne D\) holds, \(A=r\) can never be part of any solution. In general, such removals can be found by checking the consistency of the arcs — the edges — of the constraint graph, before running backtracking search at all. That's exactly the idea behind Section 4.

4. Arc Consistency and the AC-3 Algorithm

Definition

A variable \(X_i\) is arc-consistent with respect to another variable \(X_j\) if, for every value in its current domain \(D_i\), there is some value in \(D_j\) that satisfies the binary constraint on the arc \((X_i,X_j)\). A CSP is arc consistent if every variable is arc consistent with respect to every other variable.

Pseudocode — AC-3 
function AC-3(csp) returns false if an inconsistency is found and true otherwise
    queue ← a queue of arcs, initially all the arcs in csp
    while queue is not empty do
        (Xi, Xj) ← POP(queue)
        if REVISE(csp, Xi, Xj) then
            if size(Di) = 0 then return false
            for each Xk in Xi.NEIGHBOURS − {Xj} do
                add (Xk, Xi) to queue
    return true

function REVISE(csp, Xi, Xj) returns true iff the domain of Xi is revised
    revised ← false
    for each x in Di do
        if no value y in Dj allows (x, y) to satisfy the constraint between Xi, Xj then
            delete x from Di
            revised ← true
    return revised
The intuition

AC-3 keeps a queue of directed arcs (one arc per direction, for every edge in the constraint graph). It pops an arc \((X_i,X_j)\), and asks: does every remaining value of \(X_i\) still have some compatible partner left in \(D_j\)? If REVISE deletes a value from \(D_i\), then every arc pointing into \(X_i\) (from its other neighbours) might now need re-checking — so those arcs get pushed back onto the queue. This is exactly how one domain shrinking can ripple outward and shrink others.

5. Backtracking Search with an INFERENCE Function

The idea

It's also possible to incorporate consistency checks — such as arc consistency — inside the backtracking search algorithm itself, rather than as a one-time pre-processing pass. This is done using a function named INFERENCE, which imposes a consistency condition after the addition of each {var = value} to the assignment.

Pseudocode — BACKTRACK with INFERENCE 
function BACKTRACKING-SEARCH(csp) returns a solution or failure
    return BACKTRACK(csp, {})

function BACKTRACK(csp, assignment) returns a solution or failure
    if assignment is complete then return assignment
    var ← SELECT-UNASSIGNED-VARIABLE(csp, assignment)
    for each value in ORDER-DOMAIN-VALUES(csp, var, assignment) do
        if value is consistent with assignment then
            add {var = value} to assignment
            inferences ← INFERENCE(csp, var, assignment)
            if inferences ≠ failure then
                add inferences to csp
                result ← BACKTRACK(csp, assignment)
                if result ≠ failure then return result
                remove inferences from csp
            remove {var = value} from assignment
    return failure
Key takeaway — plain backtracking is a special case

The plain BACKTRACKING-SEARCH algorithm from Section 3 is exactly this algorithm with INFERENCE always returning an empty set (i.e. never inferring anything new). Every idea in this part fits into one unified picture: search plus however much consistency-checking you choose to weave in — anywhere from none (plain backtracking) to a full AC-3 pass after every assignment.

6. Where AC-3 Falls Short

Counter-example 1 — AC-3 can do nothing at all, even on a solvable CSP

Recall the full 7-variable map colouring problem from Section 1 (\(A,\dots,G\), domains \(\{r,g,b\}\), 9 constraints). Even though there are many inconsistent combinations ruled out by those constraints, the AC-3 algorithm has no effect on this problem at all — it doesn't shrink a single domain, despite the problem being solvable.

Counter-example 2 — AC-3 can even miss a CSP with NO solution

Consider colouring the three vertices of a triangle using two colours, so that no two adjacent vertices share a colour. Variables: \(A,B,C\). Domains: \(D_A=D_B=D_C=\{r,g\}\). Constraints: \(A\ne B,\ B\ne C,\ A\ne C\).

This CSP has no solution — with only 2 colours, you can never properly colour a 3-cycle (whichever colour A gets, B must differ, then C must differ from both A and B, but there are only 2 colours to choose from). Yet AC-3 has no effect on this problem either — it fails to detect the inconsistency.

Key takeaway — why this happens, and what it means

In general, AC-3 need not always reduce the domains of the variables — and even when the CSP has no solution, AC-3 is not guaranteed to reduce them either. Arc consistency only ever looks at two variables at a time, through a single binary constraint. The triangle problem's unsolvability is fundamentally a three-way interaction (A, B, and C mutually constraining each other in a cycle) — and that's structurally invisible to an algorithm that only ever checks one pair of variables against each other in isolation.

7. Generalising: k-Consistency

The natural next step

Arc consistency (which only looks at two variables at a time) is blind to inconsistencies like the two examples in Section 6. The natural way out is to look at three variables at once — this is called path consistency.

A ladder of definitions
  • Node consistency (1-consistency): a variable \(X_i\) is node consistent if every value in \(D_i\) satisfies all unary constraints on \(X_i\). A CSP is node consistent if every variable is.
  • Arc consistency (2-consistency): \(X_i\) is arc consistent with respect to \(X_j\) if for every value \(a\in D_i\), there exists \(b\in D_j\) satisfying the binary constraint on \((X_i,X_j)\). A CSP is arc consistent if every variable is arc consistent with respect to every other variable.
  • Path consistency (3-consistency): a pair \(\{X_i,X_j\}\) is path consistent with respect to \(X_m\) if for every value pair \((a,b)\in D_i\times D_j\) consistent with the \(X_i\text{-}X_j\) constraint, there exists \(c\in D_m\) satisfying both the \((X_i,X_m)\) and \((X_j,X_m)\) constraints. A CSP is path consistent if every pair is path consistent with respect to every other variable.
Definition — general k-consistency

A set of \(k-1\) variables \(\{X_1,X_2,\dots,X_{k-1}\}\) is \(k\)-consistent with respect to a variable \(X_k\) if for every \((a_1,\dots,a_{k-1})\in D_1\times\cdots\times D_{k-1}\) that's consistent with the binary constraints among \(X_1,\dots,X_{k-1}\), there exists \(a_k\in D_k\) satisfying the binary constraints on \((X_i,X_k)\) for every \(1\le i\le k-1\).

A CSP is \(k\)-consistent if every set of \(k-1\) variables is \(k\)-consistent with respect to every other variable. (Node consistency is the \(k=1\) case, arc consistency is \(k=2\), path consistency is \(k=3\) — each definition above is just this general one, specialised.)

Definition — strong k-consistency

A CSP is strongly \(k\)-consistent if it is \(k\)-consistent, \((k-1)\)-consistent, \((k-2)\)-consistent, …, 2-consistent, and 1-consistent — the whole ladder holds simultaneously, all the way down.

The beautiful theoretical payoff — strong n-consistency solves the CSP trivially

Suppose a CSP has \(n\) variables, and is made strongly \(n\)-consistent. Then a solution can be found with no search or backtracking at all:

  • Step 1: choose a consistent value for \(X_1\) (possible, since the CSP is 1-consistent).
  • Step 2: choose a consistent value for \(X_2\) (possible, since it's 2-consistent).
  • \(\vdots\)
  • Step \(n\): choose a consistent value for \(X_n\) (possible, since it's \(n\)-consistent).

At every step, strong \(k\)-consistency guarantees a compatible value exists for the next variable — so this simple greedy procedure never needs to backtrack. Worst-case time to find a solution this way: \(1+d+2d+3d+\cdots+(n-1)d = O(n^2d)\) — polynomial!

So can every CSP be solved in polynomial time? No.

Enforcing \(n\)-consistency itself must take exponential time. What does enforcing \(k\)-consistency actually require? For every relevant subset of \(k-1\) variables, we must examine which of the (up to) \(d^{k-1}\) possible joint assignments to that subset can be extended to every other variable. When \(k=n\), this means potentially reasoning about \(d^{n-1}\) possible assignments — exponential in \(n\).

Unless P = NP (a famously unsolved problem in computer science), no polynomial-time algorithm for enforcing \(n\)-consistency can exist.

The key takeaway for solving CSPs — and for this entire part
  • Do not aim for full consistency. Achieving it is just as hard as solving the original problem.
  • Aim for cheap, partial consistency as a filter before or during search.

In practice, node and arc consistency (AC-3) — and sometimes path consistency — are used not to solve the CSP outright, but to prune domains before handing the (much smaller) reduced problem to backtracking search. This is precisely the two-step recipe Section 4's worked example demonstrated directly: AC-3 first, backtracking search second — cheap filtering, then search, rather than either one alone.

1. Knowledge-Based Agents

The question this part answers

How does an agent combine what it has sensed now with what it knows in general to figure out what to do?

Definition

Knowledge-Based Agents (KBAs) are agents that explicitly store knowledge about the world in a Knowledge Base (KB) and use an inference mechanism to derive new knowledge and decide actions.

The Knowledge Base is a set of sentences in some formal language, known by a knowledge-based agent. The agent updates it with percepts and queries it to choose actions. The knowledge could be stored in logic, probability distributions, semantic networks, etc.

Three examples, across three different kinds of KB
  1. An agent navigating a maze (a logical KBA) — KB: propositional logic sentences describing which cells have obstacles, which are safe/unsafe, which give reward/penalty. Inference: logical entailment (model checking, resolution) to deduce safe squares.
  2. A medical diagnosis system with Bayesian Networks (a probabilistic KBA) — KB: conditional probability tables (CPTs). Inference: Bayes' theorem, updating disease probabilities given symptoms.
  3. A plant identification assistant (a semantic-network-based KBA) — KB: a semantic network representing plant categories and their properties (typically a directed graph, concepts as vertices, relations as edges). Inference: graph traversal and relation chaining.
The five functions used in a Knowledge-Based Agent program
  • TELL — adds new sentences to the knowledge base.
  • ASK — queries what is known.
  • MAKE-PERCEPT-SENTENCE — constructs a sentence asserting that the agent perceived the given percept at the given time.
  • MAKE-ACTION-QUERY — constructs a sentence asking what action should be done at the current time.
  • MAKE-ACTION-SENTENCE — constructs a sentence asserting that the chosen action was executed.
The Knowledge-Based Agent program 
function KB-AGENT(percept) returns an action
    persistent: KB, a knowledge base
                t, a counter indicating time (initially 0)

    action ← ASK(KB, MAKE-ACTION-QUERY(t))
    TELL(KB, MAKE-ACTION-SENTENCE(action, t))
    t ← t+1
    return action

Every cycle: tell the KB what was just perceived, ask the KB what to do, tell the KB what was actually done, advance the clock. The entire "intelligence" of the agent lives inside how ASK is implemented — which is exactly what the rest of this part is about.

5. Models and Entailment

Definition — Model

A model is an assignment of a truth value to every propositional symbol (a "possible world"). Example: \(P\): "Today is Monday", \(Q\): "There is a quiz scheduled for today." \(\{P=\text{true}, Q=\text{false}\}\) is a model.

Note: with \(n\) propositional symbols, the number of possible models is \(2^n\).

Definition — Entailment

A sentence \(P\) entails a sentence \(Q\) (written \(P\models Q\)) if in every model in which \(P\) is true, \(Q\) is also true.

Equivalently: \(P\models Q\) iff \(P\Rightarrow Q\) is a tautology (always true, in every possible model).

KB: "All men are mortal", "Socrates is a man." \(\alpha\): "Socrates is mortal."

\(\big[\forall x\, \text{Man}(x)\Rightarrow\text{Mortal}(x)\big] \land \text{Man}(\text{Socrates}) \models \text{Mortal}(\text{Socrates})\)

In every model where KB is true, \(\alpha\) is also true — so \(KB\models\alpha\).

Non-examples — entailment is about structure, not "meaning"

\(P\): "2 is odd." \(Q\): "Paris is in France." \(P\) does not entail \(Q\), even though \(P\Rightarrow Q\) happens to be (vacuously) true in the "usual" world — there's no necessary logical link forcing \(Q\) whenever \(P\) holds.

\(P\): "\(n\) is divisible by 4." \(Q\): "\(n\) is even." \(P\) does not entail \(Q\) either, even though \(P\Rightarrow Q\) is true under the usual axioms of arithmetic — entailment can't "know" those axioms; it only cares about whether the sentence structure forces the conclusion.

Entailment does not care what the words/predicates in the sentences "actually mean." It only cares about the structural pattern. \(KB\models\alpha\) means: for every possible model — even any bizarre reinterpretation you could dream up — if that model satisfies KB, it is forced to also satisfy \(\alpha\). Equivalently: \(KB\models\alpha\) if and only if there is no model that satisfies KB but fails to satisfy \(\alpha\).

Entailment only exists when there is a necessary logical link. Otherwise, changing interpretations (models) will break it.

The formal, set-theoretic view — and why it matters

Let \(M(\alpha)\) and \(M(\beta)\) be the sets of models in which \(\alpha\) and \(\beta\) are true, respectively. Then:

\(\alpha\models\beta\)  if and only if  \(M(\alpha)\subseteq M(\beta)\)

Model checking is exactly this: a way of checking whether \(\alpha\models\beta\) by checking whether \(M(\alpha)\subseteq M(\beta)\) — precisely what every truth table above has been doing, one row (one model) at a time.

The problem with brute-force model checking

To check \(KB\models\alpha\), where KB and \(\alpha\) together contain \(n\) propositional symbols: an algorithm that generates and stores all \(2^n\) possible models to check each one takes \(O(n\cdot2^n)\) space. The TT-ENTAILS? algorithm (next section) is a recursive algorithm that needs only \(O(n)\) space, by generating models one at a time via a depth-first search over the binary tree of models.

6. TT-ENTAILS? — Deciding Entailment by Model Checking

Pseudocode 
function TT-ENTAILS?(KB, α) returns true or false
    symbols ← a list of the proposition symbols in KB and α
    return TT-CHECK-ALL(KB, α, symbols, {})

function TT-CHECK-ALL(KB, α, symbols, model) returns true or false
    if EMPTY?(symbols) then
        if PL-TRUE?(KB, model) then return PL-TRUE?(α, model)
        else return true   (When KB is false, always return true)
    else
        P ← FIRST(symbols)
        rest ← REST(symbols)
        return (TT-CHECK-ALL(KB, α, rest, model ∪ {P=true})
               and
               TT-CHECK-ALL(KB, α, rest, model ∪ {P=false}))

The recursion picks one symbol at a time, branches on true/false, and only actually evaluates KB and α once every symbol has a value (the base case). Note the deliberately generous base case: if KB turns out to be false in that particular complete model, the model is irrelevant to entailment, so the function just returns true and lets the other branch carry the real work.

Worked Example 1 — does A∧B entail A?

\(KB=A\land B\), \(\alpha=A\). \(\text{symbols}=[A,B]\).

Branch 1 — TT-CHECK-ALL(KB,α,[B],{A=true}):

  {A=true,B=true}: PL-TRUE?(KB)=T∧T=true → return PL-TRUE?(α)=A=true

  {A=true,B=false}: PL-TRUE?(KB)=T∧F=false → KB false, return true

  true AND true = true

Branch 2 — TT-CHECK-ALL(KB,α,[B],{A=false}):

  {A=false,B=true}: PL-TRUE?(KB)=F∧T=false → KB false, return true

  {A=false,B=false}: PL-TRUE?(KB)=F∧F=false → KB false, return true

  true AND true = true

Root: true (Branch 1) AND true (Branch 2) = true

So TT-ENTAILS?(A∧B, A) returns true, that is, A∧B ⊨ A.
Worked Example 2 — does A∨B entail A?

\(KB=A\lor B\), \(\alpha=A\). \(\text{symbols}=[A,B]\).

Branch 1 — TT-CHECK-ALL(KB,α,[B],{A=true}):

  {A=true,B=true}: PL-TRUE?(KB)=T∨T=true → return PL-TRUE?(α)=A=true

  {A=true,B=false}: PL-TRUE?(KB)=T∨F=true → return PL-TRUE?(α)=A=true

  true AND true = true

Branch 2 — TT-CHECK-ALL(KB,α,[B],{A=false}):

  {A=false,B=true}: PL-TRUE?(KB)=F∨T=true → return PL-TRUE?(α)=A=false

  {A=false,B=false}: PL-TRUE?(KB)=F∨F=false → KB false, return true

  false AND true = false

Root: true (Branch 1) AND false (Branch 2) = false

So TT-ENTAILS?(A∨B, A) returns false, that is, A∨B ⊭ A.

Makes sense: in the model {A=false, B=true}, A∨B is true but A itself is false — exactly the one "escaping" model that breaks entailment, and exactly the branch that returns false above.

What the algorithm is really computing, and its cost

TT-ENTAILS?(KB,\(\alpha\)) returns the truth value of: for every model \(m\), \(m\in M(KB)\Rightarrow m\in M(\alpha)\) — that is, \(M(KB)\subseteq M(\alpha)\), which is exactly \(KB\models\alpha\).

The time complexity of TT-ENTAILS? is \(O(2^n)\), where \(n\) is the total number of propositional symbols in KB and \(\alpha\) — it still has to branch all the way down to a complete model before it can conclude anything.

The real weakness — TT-ENTAILS? can't detect failure early

In the \(A\land B\models A\) trace above: once \(A=\text{false}\) is assigned, \(KB=A\land B\) is already false, whatever \(B\) turns out to be. But the algorithm still branches on \(B\) and evaluates both leaves, only to find "KB false, return true" both times — wasted work. In general, the algorithm always builds out every branch and checks all \(2^n\) complete models before answering, because it only evaluates KB once every symbol has a value, and never looks at KB with a partial model.

What's needed is a cheap test on a partial model: "is KB already false, or already true?" Conjunctive Normal Form (CNF) makes this test trivial — built from literals and clauses, which is exactly where Section 7 begins.

7. Literals, Clauses, and the Resolution Rules

Definitions

A literal is either an atomic sentence (a positive literal) or a negated atomic sentence (a negative literal). E.g. \(P,Q,W_{31}\) are positive; \(\neg P,\neg Q,\neg P_{12}\) are negative.

A clause is a disjunction of literals. E.g. \(P\lor Q\lor R\),   \(P\lor Q\lor\neg R\lor S\),   \(P_{13}\lor P_{22}\).

The Unit Resolution Rule

\[ (l_1\lor l_2\lor\cdots\lor l_k)\land m \models l_1\lor\cdots\lor l_{i-1}\lor l_{i+1}\lor\cdots\lor l_k \]

where each \(l_j\) and \(m\) are literals, and \(l_i\) and \(m\) are complementary (negations of each other).

Modus Ponens is just a special case

\((P\Rightarrow Q)\land P\models Q\) is exactly \((\neg P\lor Q)\land P\models Q\) — a unit resolution where the "clause" is \(\neg P\lor Q\) (using Implication Elimination) and the single literal is \(P\), complementary to \(\neg P\).

The Full Resolution Rule

\[ (l_1\lor\cdots\lor l_k)\land(m_1\lor\cdots\lor m_n) \models l_1\lor\cdots\lor l_{i-1}\lor l_{i+1}\lor\cdots\lor l_k\lor m_1\lor\cdots\lor m_{j-1}\lor m_{j+1}\lor\cdots\lor m_n \]

where \(l_i\) and \(m_j\) are complementary literals. In words: take two clauses, find one complementary pair of literals between them, and the resolvent is everything else from both clauses, OR'd together.

Worked example — proving the resolution rule directly

\(k=2\), \(n=2\): \((P\lor Q)\land(\neg P\lor R) \models Q\lor R\).

Proof. Suppose \((P\lor Q)\land(\neg P\lor R)\) is true — so both \(P\lor Q\) and \(\neg P\lor R\) are true. To show: \(Q\lor R\) is true.

Case 1: \(P\) is false. Then since \(P\lor Q\) is true, \(Q\) must be true.

Case 2: \(P\) is true. Then since \(\neg P\lor R\) is true, \(R\) must be true.

Hence one of \(Q,R\) is true — so \(Q\lor R\) is true. ∎

A trap worth knowing — can you resolve two complementary pairs at once?

Does \((P\lor Q\lor R)\land(\neg P\lor\neg Q\lor S) \models R\lor S\)? No. In the model \(\{P=\text{true},Q=\text{false},R=\text{false},S=\text{false}\}\): the left side is true, but \(R\lor S\) is false. Resolution only ever removes exactly one complementary pair at a time — trying to cancel both \(P/\neg P\) and \(Q/\neg Q\) simultaneously is not a valid inference.

Why any of this matters — the fact the whole Resolution algorithm rests on

Every sentence in propositional logic is logically equivalent to a conjunction of clauses.

Once every sentence can be rewritten this way, resolution — a single, simple, mechanical rule — is the only inference rule you ever need to decide entailment. That rewriting is called Conjunctive Normal Form, covered next.

8. Conjunctive Normal Form & the Resolution Algorithm

Definition — Conjunctive Normal Form (CNF)

A sentence expressed as a conjunction of clauses is said to be in CNF. E.g. \((P\lor Q\lor R)\land(R\lor\neg S)\),   \((\neg P\lor Q)\land(P\lor R)\land(\neg R\lor S)\),   \(P\land(Q\lor\neg R)\).

Worked Example 1 — converting a biconditional to CNF

Convert \(B_{11}\Leftrightarrow P_{12}\lor P_{21}\) (recall this is \(R_2\) from the Wumpus World) into CNF.

Biconditional Elimination: \((B_{11}\Rightarrow P_{12}\lor P_{21})\land(P_{12}\lor P_{21}\Rightarrow B_{11})\)

Converting conditionals to disjunctions: \((\neg B_{11}\lor(P_{12}\lor P_{21}))\land(\neg(P_{12}\lor P_{21})\lor B_{11})\)

De Morgan's law: \((\neg B_{11}\lor P_{12}\lor P_{21})\land\big((\neg P_{12}\land\neg P_{21})\lor B_{11}\big)\)

Right Distributive law:

\((\neg B_{11}\lor P_{12}\lor P_{21}) \land (\neg P_{12}\lor B_{11}) \land (\neg P_{21}\lor B_{11})\)

Worked Example 2 — a messier sentence

Convert \(\neg(P\Rightarrow Q)\lor(Q\land R\land\neg S)\) into CNF.

Conditional to disjunction: \(\neg(\neg P\lor Q)\lor(Q\land R\land\neg S)\)

De Morgan's law: \((P\land\neg Q)\lor(Q\land R\land\neg S)\)

Left Distributive law: \(\big((P\land\neg Q)\lor Q\big)\land\big((P\land\neg Q)\lor R\big)\land\big((P\land\neg Q)\lor\neg S\big)\)

Right Distributive law: \((P\lor Q)\land(\neg Q\lor Q)\land(P\lor R)\land(\neg Q\lor R)\land(P\lor\neg S)\land(\neg Q\lor\neg S)\)

Since \(\neg Q\lor Q\equiv\mathbf{T}\), that clause drops out:

\((P\lor Q)\land(P\lor R)\land(\neg Q\lor R)\land(P\lor\neg S)\land(\neg Q\lor\neg S)\)

Validity and Satisfiability

A sentence is valid if it is true in all models — valid sentences are called tautologies. A sentence is satisfiable if it is true in at least one model.

Note: \(P\) is valid iff \(\neg P\) is not satisfiable; \(P\) is satisfiable iff \(\neg P\) is not valid.

The chain that makes resolution-based refutation work

\(\alpha\models\beta\)

\(\Leftrightarrow\ \alpha\Rightarrow\beta\) is valid.

\(\Leftrightarrow\ \neg(\alpha\Rightarrow\beta)\) is not satisfiable.

\(\Leftrightarrow\ \neg(\neg\alpha\lor\beta)\) is not satisfiable.

\(\Leftrightarrow\ \alpha\land\neg\beta\) is not satisfiable.  (proof by contradiction)

This is the entire strategy behind PL-RESOLUTION: to prove \(KB\models\alpha\), show that \(KB\land\neg\alpha\) can never be satisfied — by resolving clauses together until an outright contradiction (the empty clause) is derived.

Pseudocode — PL-RESOLUTION 
function PL-RESOLUTION(KB, α) returns true or false
    clauses ← the set of clauses in the CNF representation of KB ∧ ¬α
    new ← {}
    while true do
        for each pair of clauses Ci, Cj in clauses do
            resolvents ← PL-RESOLVE(Ci, Cj)
            if resolvents contains the empty clause then return true
            new ← new ∪ resolvents
        if new ⊆ clauses then return false
        clauses ← clauses ∪ new

Negate the query, throw it in with the KB's clauses, and keep resolving pairs. Derive the empty clause (a direct contradiction) and KB⊨α is proven. Run out of new resolvents to add without ever hitting a contradiction, and KB⊭α.

Worked Example — running PL-RESOLUTION

KB: \((P\lor\neg Q)\land(Q\lor R)\land(\neg P\lor R)\). Query \(\alpha:R\). Negating \(\alpha\) and combining: \(\text{clauses}=\{P\lor\neg Q,\ Q\lor R,\ \neg P\lor R,\ \neg R\}\), labelled \(C_1,C_2,C_3,C_4\) (negated \(\alpha\)).

Level 1 (input): \(C_1=P\lor\neg Q\), \(C_2=Q\lor R\), \(C_3=\neg P\lor R\), \(C_4=\neg R\) (negated \(\alpha\)).

Level 2 (all pairwise resolvents): \(C_1{+}C_2\to P\lor R\);  \(C_1{+}C_3\to\neg Q\lor R\);  \(C_1{+}C_4\to\) none (no complementary pair);  \(C_2{+}C_3\to\) none;  \(C_2{+}C_4\to Q\);  \(C_3{+}C_4\to\neg P\).

Level 3: resolve \((P\lor R)\) with \(C_3=\neg P\lor R\) on \(P/\neg P\): \(R\lor R=R\).

Level 4: resolve \(R\) with \(C_4=\neg R\): the empty clause.

Therefore, PL-RESOLUTION returns true — that is, KB ⊨ R.

9. The SAT Problem and the DPLL Algorithm

The Boolean Satisfiability (SAT) Problem

The problem of determining if there exists an interpretation (a model) that satisfies a given Boolean formula. It was the first problem proved to be NP-complete (1970s).

Cook-Levin Theorem: The Boolean Satisfiability Problem is NP-complete.

The DPLL Algorithm (Davis, Putnam, Logemann, Loveland)

Checks satisfiability of a propositional sentence, using three improvements over the simple scheme of TT-ENTAILS?:

  1. Early termination
  2. Pure symbol heuristic
  3. Unit clause heuristic
1. Early termination

Detects whether the sentence must be true or false, even with a partially completed model. A clause is true if any literal is true; a sentence is false if any clause is false; a sentence is true if all clauses are true.

2. Pure symbol heuristic

A pure symbol is one that appears with the same "sign" in every clause. For the sentence to be true, a model must assign pure symbols so as to make their literals true.

Precise definition, as DPLL uses it: let \(S\) be a set of clauses and \(m\) a partial model. A symbol \(P\) is pure w.r.t. \((S,m)\) if: (1) \(P\) is unassigned in \(m\); (2) \(P\) occurs in at least one clause of \(S\) not yet true in \(m\); (3) in all such not-yet-true clauses, \(P\) occurs with the same sign. Occurrences of \(P\) in clauses already made true by \(m\) are ignored.

3. Unit clause heuristic

A unit clause is a clause in which all literals except one are already assigned false by the model.

Precise definition: a clause \(C\in S\) is a unit clause w.r.t. \((S,m)\) if exactly one literal \(l\) of \(C\) is unassigned, and every other literal of \(C\) is false in \(m\). Then \(l\) is the unit literal. If \(l=P\), FIND-UNIT-CLAUSE returns \((P,\text{true})\); if \(l=\neg P\), it returns \((P,\text{false})\). If several unit clauses exist, any one can be chosen.

Pseudocode — DPLL 
function DPLL-SATISFIABLE?(s) returns true or false
    clauses ← the set of clauses in the CNF representation of s
    symbols ← a list of the proposition symbols in s
    return DPLL(clauses, symbols, {})

function DPLL(clauses, symbols, model) returns true or false
    if every clause in clauses is true in model then return true
    if some clause in clauses is false in model then return false
    P, value ← FIND-PURE-SYMBOL(symbols, clauses, model)
    if P is non-null then return DPLL(clauses, symbols−P, model ∪ {P=value})
    P, value ← FIND-UNIT-CLAUSE(clauses, model)
    if P is non-null then return DPLL(clauses, symbols−P, model ∪ {P=value})
    P ← FIRST(symbols)
    rest ← REST(symbols)
    return DPLL(clauses, rest, model ∪ {P=true}) or
             DPLL(clauses, rest, model ∪ {P=false})

Check the two easy exits first (all true / some false), then try pure symbol, then unit clause, and only then fall back to plain branching on the first remaining symbol. This ordering is exactly why DPLL beats TT-ENTAILS? — it resolves as much as it can for free before ever guessing.

10. Horn Clauses and Forward Chaining

Definite Clauses and Horn Clauses

A clause in which exactly one literal is positive is a definite clause. E.g. \(\neg P\lor\neg Q\lor R\), \(P\lor\neg Q\). (\(P\lor\neg Q\lor R\) is not definite — two positive literals.)

A clause in which at most one literal is positive is a Horn clause. E.g. \(\neg P\lor\neg Q\lor R\), \(\neg P\lor\neg Q\). (\(P\lor\neg Q\lor R\) is not Horn either.)

Two properties worth remembering
  • Every definite clause is a Horn clause (a definite clause is just the special case with exactly one positive literal, rather than "at most" one).
  • Horn clauses are closed under resolution — resolving two Horn clauses always yields another Horn clause. E.g. \((\neg P\lor\neg Q\lor R)\land(\neg P\lor\neg Q\lor\neg R)\models\neg P\lor\neg Q\) — Horn, Horn, and the resolvent is Horn too.
Every Horn clause can be written as an implication

Multiple literals, one positive (also definite): \(\neg P\lor\neg Q\lor R \equiv \neg(P\land Q)\lor R \equiv (P\land Q)\Rightarrow R\)

A single positive literal (also definite): \(P \equiv \mathbf{T}\Rightarrow P\)

No positive literals: \(\neg P\lor\neg Q \equiv \neg(P\land Q) \equiv (P\land Q)\Rightarrow\mathbf{F}\);   \(\neg P\equiv P\Rightarrow\mathbf{F}\)

This "implication form" is exactly what Forward and Backward Chaining are built on — every Horn-clause KB can be read as a set of if-then rules, with plain facts as \(\mathbf{T}\Rightarrow P\) rules.

Pseudocode — Forward Chaining (PL-FC-ENTAILS?) 
function PL-FC-ENTAILS?(KB, q) returns true or false
    inputs: KB, a set of propositional definite clauses; q, a proposition symbol
    count ← a table; count[c] initially = number of symbols in clause c's premise
    inferred ← a table; inferred[s] initially false for all symbols
    queue ← a queue of symbols, initially the symbols known to be true in KB

    while queue is not empty do
        p ← POP(queue)
        if p = q then return true
        if inferred[p] = false then
            inferred[p] ← true
            for each clause c in KB where p is in c.PREMISE do
                decrement count[c]
                if count[c] = 0 then add c.CONCLUSION to queue
    return false

The idea: start from known facts, and every time a rule's entire premise has been established (its count hits 0), its conclusion becomes newly known too — keep going until the query pops out of the queue, or the queue runs dry.

Worked example

KB: \(A,\ B,\ \neg A\lor\neg B\lor L,\ \neg A\lor\neg P\lor L,\ \neg B\lor\neg L\lor M,\ \neg L\lor\neg M\lor P,\ \neg P\lor Q\). Query \(q=Q\).

As implications: \(A\) (fact), \(B\) (fact), \(A\land B\Rightarrow L\), \(A\land P\Rightarrow L\), \(B\land L\Rightarrow M\), \(L\land M\Rightarrow P\), \(P\Rightarrow Q\).

\(\text{inferred}[s]=\text{false}\) for all \(s\); \(\text{queue}=\{A,B\}\).

1) \(p\gets A\). inferred[A]←true.

2) \(p\gets B\). inferred[B]←true. \(A\land B\Rightarrow L\)'s count hits 0 → add \(L\) to queue.

3) \(p\gets L\). inferred[L]←true. \(B\land L\Rightarrow M\)'s count hits 0 → add \(M\) to queue.

4) \(p\gets M\). inferred[M]←true. \(L\land M\Rightarrow P\)'s count hits 0 → add \(P\) to queue.

5) \(p\gets P\). inferred[P]←true. \(P\Rightarrow Q\)'s count hits 0 → add \(Q\) to queue.

6) \(p\gets Q\). \(p=q\) → return true.

Note \(A\land P\Rightarrow L\) never actually fires (its count only reaches 1, since \(P\) isn't known until step 5, by which point \(L\) is already inferred via the other rule) — a reminder that with two ways to reach the same conclusion, forward chaining only needs one of them to succeed.

11. Backward Chaining

The idea — work backwards from the query

To prove \(q\) by backward chaining: if \(q\) is already known true, there's nothing to do. Otherwise, prove by backward chaining all premises of some implication in KB whose conclusion is \(q\) (each premise becomes a new subgoal). For every new subgoal: (i) avoid loops — check if it's already on the current goal stack; (ii) avoid repeated work — check if it's already been proved true or already failed. If all subgoals are proven, the goal is proven; otherwise the attempt fails.

Pseudocode — Backward Chaining (PL-BC-ENTAILS?) 
function PL-BC-ENTAILS?(KB, q) returns true or false
    return BC-OR(KB, q, {})  ({} = empty set of goals already on the path)

function BC-OR(KB, q, path) returns true or false
    q: the current goal; path: symbols already being proved (cycle detection)
    if q is known to be true in KB then return true
    if q ∈ path then return false  (q depends on itself)
    for each clause c in KB where q = c.CONCLUSION do
        if BC-AND(KB, c.PREMISE, {q} ∪ path) then return true
    return false

function BC-AND(KB, premises, path) returns true or false
    if premises = {} then return true
    p ← FIRST(premises); rest ← REST(premises)
    return BC-OR(KB, p, path) and BC-AND(KB, rest, path)

BC-OR tries every rule that could conclude \(q\) (an OR over rules); BC-AND requires every premise of one chosen rule to succeed (an AND over premises). The two functions call each other, exactly mirroring the AND-OR structure of the proof tree below.

Worked Example 1

KB: \(D,\ E,\ A\land B\Rightarrow C,\ D\Rightarrow B,\ E\Rightarrow A\). Query \(q=C\).

Both \(A\) (via \(E\Rightarrow A\), and \(E\) is a fact) and \(B\) (via \(D\Rightarrow B\), and \(D\) is a fact) are proven — so the AND at \(A\land B\Rightarrow C\) succeeds, and \(C\) is proven.

Worked Example 2 — a failed branch, and backtracking to a successful one

KB: \(A,\ B,\ M,\ \neg P\lor Q,\ \neg L\lor\neg M\lor Q,\ \neg A\lor\neg P\lor L,\ \neg B\lor L\). Query \(q=Q\).

As implications: \(P\Rightarrow Q\) (clause 1), \(L\land M\Rightarrow Q\) (clause 2), \(A\land P\Rightarrow L\) (clause 3), \(B\Rightarrow L\) (clause 4), \(\mathbf{T}\Rightarrow A\) (clause 5), \(\mathbf{T}\Rightarrow B\) (clause 6), \(\mathbf{T}\Rightarrow M\) (clause 7). Notice: \(P\) has no defining clause at all — anything requiring \(P\) is doomed to fail.

Tracing it through: Q(OR) first tries clause 1 (\(P\Rightarrow Q\)) — needs \(P\), which has no defining clause, so this branch fails, backtracks. Q(OR) then tries clause 2 (\(L\land M\Rightarrow Q\), an AND) — needs both \(L\) and \(M\). \(M\) succeeds immediately (fact). For \(L\)(OR): first tries clause 3 (\(A\land P\Rightarrow L\)) — \(A\) succeeds (fact), but \(P\) fails again (no defining clause) — clause 3 fails even though half of it succeeded. \(L\)(OR) then tries clause 4 (\(B\Rightarrow L\)) — \(B\) succeeds (fact) — so \(L\) succeeds via clause 4. With both \(L\) and \(M\) proven, clause 2's AND succeeds, and Q is proven true.

This example exists specifically to show backward chaining recovering from a dead end — failing down the clause-3 path doesn't sink the whole proof, because \(L\)(OR) simply tries its next alternative, clause 4.

Key takeaway

Backward chaining does a Depth-First Search of the AND-OR graph of the KB, starting from the node corresponding to the query.

12. Comparison: Forward Chaining vs. Backward Chaining

Forward ChainingBackward Chaining
Data-driven — starts from known facts and works toward whatever they imply.Goal-driven — starts from the query and works backward toward facts.
Time complexity is linear in the size of the KB (total number of literals across all definite/Horn clauses).Time complexity can be much less than linear in the size of the KB — though in the worst case, it can still be linear.
What this whole part adds up to

Five algorithms, one underlying question: given what an agent knows, what else must be true? TT-ENTAILS? answers this by brute force (every model, checked exhaustively). Resolution answers it by refutation (assume the opposite, derive a contradiction). DPLL answers a closely related question — is this even satisfiable at all? — using the same refutation idea, sped up with two genuinely simple heuristics. And once the knowledge base is restricted to Horn clauses, Forward and Backward Chaining answer it directly and efficiently, from opposite ends of the same AND-OR graph. Every one of these is really the same core idea — entailment as "no escaping model" — wearing a different, progressively more efficient, disguise.

Mini glossary

PerceptA single piece of sensory input an agent receives.
FrontierThe set of discovered-but-not-yet-explored nodes in a search.
g(n)The actual cost paid so far to reach node \(n\).
h(n)The estimated cost still remaining from \(n\) to the goal.
f(n)The evaluation function used to rank nodes in Best-First Search (e.g. \(g\), \(g+h\), or \(h\) alone).
AdmissibleA heuristic that never overestimates the true remaining cost.
ConsistentA stronger, triangle-inequality-style version of admissibility.
Local optimumA state that's better than all its neighbours, but not the best possible state overall.
FitnessIn evolutionary algorithms, a score measuring how good a candidate solution is.
Minimax valueThe utility of a state for MAX, assuming both players play optimally from there to the end of the game.
Zero-sum gameA game where one player's gain is exactly the other's loss — what's good for MAX is equally bad for MIN.
α (alpha)The best value MAX can guarantee so far, along the current path from the root.
β (beta)The best value MIN can guarantee so far, along the current path from the root.
PruningSkipping a branch of the search tree that's been proven irrelevant to the final decision, without ever evaluating it.
Evaluation functionA heuristic estimate of how good a non-terminal position is, used when a full search to terminal states isn't feasible.
CSPConstraint Satisfaction Problem — defined by variables, their domains, and constraints on allowable combinations of values.
Consistent assignmentAn assignment of values that violates no constraints (may be partial or complete).
Constraint graphA graph with one node per CSP variable, and an edge between any two variables that share a constraint.
Arc consistencyA variable \(X_i\) is arc consistent w.r.t. \(X_j\) if every remaining value in \(D_i\) has at least one compatible value left in \(D_j\).
AC-3The standard algorithm for enforcing arc consistency across an entire CSP, by repeatedly revising domains until no arc can shrink any further.
k-consistencyThe general pattern behind node/arc/path consistency: any consistent assignment to \(k-1\) variables can always be extended to a \(k\)th, for every choice of that \(k\)th variable.
Entailment (KB ⊨ α)Every model that satisfies KB also satisfies α — there's no escaping model. Equivalent to KB∧¬α being unsatisfiable.
CNFConjunctive Normal Form — a sentence written as a conjunction of clauses (disjunctions of literals). Every propositional sentence can be rewritten this way.
ResolutionThe single inference rule that resolves two clauses on a complementary literal pair; repeatedly applying it to KB∧¬α until the empty clause appears proves KB⊨α.
Horn clauseA clause with at most one positive literal — always expressible as an implication, and the basis for both Forward and Backward Chaining.
Forward / Backward ChainingTwo ways to decide entailment over a Horn-clause KB: forward chains from known facts toward the query (data-driven); backward chains from the query toward known facts (goal-driven), via an AND-OR graph search.
