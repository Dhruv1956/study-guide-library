Lecture 1

Foundations — What Is an Algorithm, and How Do We Measure One?

This opening lecture does three things: it defines "algorithm" precisely (with a detour into where the word itself comes from), walks through Bubble Sort as a first concrete example, and introduces the three symbols — Big-O, Big-Ω, Big-Θ — that will describe every algorithm's running time for the rest of the course.

1.1 · What is an algorithm?

Story — where the word "algorithm" comes from

The word traces back to Al-Khwārizmī, a 9th-century Persian mathematician. His name, Latinized, became "Algorithmi." One of his works was titled (in its Latin form) Algorithmi de Numero Indorum — "Al-Khwārizmī on the numbers of the Indians" — referring to the Hindu–Arabic numeral system he helped popularize. Over centuries, "Algorithmi" drifted into the modern word "algorithm."

Before writing down a formal definition, think about what any procedure needs, in the most general possible terms:

  • Input — something to work on.
  • Process — a well-defined instruction, or sequence of well-defined instructions, applied to that input.
  • Output — the result once the process finishes.

Putting these together gives an informal description: a sequence of well-defined instructions, with an input and an output. Drawn as a flow, this is simply:

Input → Process → Output

One subtlety worth sitting with: the input and output can each be finite or infinite in principle, but the process itself is only allowed to take a finite amount of time. That restriction is what turns "a sequence of instructions" into something we'd actually call an algorithm.

Definition — Algorithm

An algorithm is a sequence of well-defined operations, taking an input, processing it, to give an output, in finite time.

Two requirements are packed into this definition, and both matter:

  • An algorithm must be correct — it has to actually produce the right output.
  • An algorithm must run for a finite number of steps — it must terminate.

The central question: how long does it take?

Once we accept that an algorithm always finishes, the natural next question is: how long does it take, and does that depend on how much data we feed it? Write \(n\) for the size of the input. Then the running time is some function of \(n\):

$$T(n) = \,?$$

Time complexity is a function of \(n\), the input size. This single idea — that running time should be measured as a function of input size, not as a fixed number of seconds on one particular machine — is the foundation the entire course is built on.

This naturally splits the study of algorithms, which we call Analysis, into two branches:

Analysis has two branches
  • Time Complexity — how many basic operations does the algorithm perform, as a function of \(n\)?
  • Space Complexity — how much extra memory does it use, as a function of \(n\)?
Common confusion — which case are we analysing?

By default, "the" analysis of an algorithm means its worst-case behaviour — not the best case. When we later ask "how many comparisons does this algorithm make?" without further qualification, we mean: what is the largest number of comparisons it could possibly be forced to make, over every input of size \(n\)?

Story — Donald Knuth and the father of the field

Donald Knuth wrote mathematical volumes about algorithms — The Art of Computer Programming — rather than an ordinary programming textbook. He is often called the father of the analysis of algorithms; he is also the creator of TeX (the typesetting system much of mathematical writing still relies on today), a theoretical computer scientist and mathematician, and a Turing Award winner.

Story — a question posed to Barack Obama

President Obama was once asked, in a lighthearted interview: "How do you sort 10 million numbers in a good way?" His answer, memorably: "I'm sure Bubble Sort is not a good way to go about it." It's a fun anecdote — but it's also exactly the right instinct, and Bubble Sort is precisely where this course starts, so we can see concretely why it isn't a good way, before moving to algorithms that are.

1.2 · Bubble Sort, worked by hand

Bubble Sort is the simplest sorting algorithm there is: repeatedly step through the array, and whenever two neighbouring elements are in the wrong order, swap them. Do enough passes, and the array ends up sorted.

Worked example

With \(n=6\), the output appears after exactly \(n-1=5\) steps — and this number is finite, exactly as the definition of an algorithm requires.

Analysis: what actually gets counted?

A ground rule for all analysis

The analysis of an algorithm must be independent of hardware and software (independent of the programming language used). We can't measure "how many seconds" — that depends on the machine. Instead, we count operations.

So: what operations does Bubble Sort actually perform?

  1. Comparisons (the basic operation — deciding whether to swap)
  2. Exchanges (the swaps themselves)

Counting the comparisons

From the trace above: step 1 makes 5 comparisons, step 2 makes 4, step 3 makes 3, step 4 makes 2, step 5 makes 1. In general, for input size \(n\), the pattern is \((n-1) + (n-2) + \cdots + 1\).

Story — young Gauss and the sum 1 + 2 + ... + 100

This is exactly the sum famously posed to Carl Friedrich Gauss as a schoolboy: add up 1 through 100. His trick: pair the first and last term, the second and second-last, and so on.

$$5+4+3+2+1 = 15$$

For 1 through 100: write the sum forwards and backwards, and add:

$$\underbrace{100+99+\cdots+2+1}_{\text{50 pairs}}$$

Each of the 50 pairs (100&1, 99&2, ..., 51&50) adds to 101, so the sum is \(101\times50=5050\). A slightly different pairing makes the general pattern clearer: write \(101+100+\cdots+1+0\) — that's 51 pairs, each summing to 101 (e.g. \(101+0\), \(100+1\), ...), giving \(101\times51=5151\) — and this trick "repeats itself" for any such sum, which is exactly what lets us write down the general formula \(\dfrac{n(n+1)}{2}\).

Deriving the general sum \(S = 1+2+\cdots+(n-1)\)

Write the sum \(S\) forwards and backwards, then add the two copies term by term:

$$S = 1+2+\cdots+(n-1)$$

$$S = (n-1)+(n-2)+\cdots+1$$

Adding vertically, every column sums to \(n\), and there are \((n-1)\) columns:

$$2S = (n-1)\cdot n \quad\Longrightarrow\quad S = \frac{n(n-1)}{2}$$

∎

Key result — comparisons in Bubble Sort

$$T(n) = \frac{n(n-1)}{2} = \text{number of comparisons, given input of size } n$$

This is exactly what "time complexity" means in practice: a formula, in terms of \(n\), for how much work the algorithm does.

1.3 · Exchanges, and the shape of the answer

The same style of argument handles the number of exchanges. In the worst case, the number of exchanges made during step \(i\) is precisely \((n-i)\), for \(i=1,\dots,n-1\) — exactly mirroring the comparison count. So:

$$\text{Total exchanges (worst case)} = (n-1)+(n-2)+\cdots+1 = \frac{n(n-1)}{2}$$

Comparing algorithms means analysing the total time complexity found this way. Here, both quantities — comparisons and exchanges — come out to \(\dfrac{n(n-1)}{2}\), a polynomial of degree 2 in \(n\). This is why Bubble Sort is described as having quadratic growth: double the input, and the work roughly quadruples.

Why a whole new notation is worth having

We now have an exact formula, \(\frac{n(n-1)}{2}\). So why would we ever want anything less precise than this? Because exact formulas get unwieldy fast (later algorithms won't have such clean closed forms), and because what we usually care about is the shape of the growth — is it linear, quadratic, exponential? — not the exact constant. This motivates comparing a function \(f(x)\) against a simpler reference function \(g(x)\), asking only whether \(f\) is bounded above or bounded below by some constant multiple of \(g\), from some point onward.

1.4 · Big-O, Big-Ω, Big-Θ

Definition 1 — Big-O (bounded above)

\(f(x)\) is bounded above by \(g(x)\), written \(f(x)\in O(g(x))\), if there exist constants \(c>0\) and \(x_0\) such that

$$f(x)\le c\,g(x) \qquad \text{for all } x\ge x_0.$$

Definition 2 — Big-Ω (bounded below)

\(f(x)\) is bounded below by \(g(x)\), written \(f(x)\in\Omega(g(x))\), if there exist constants \(c>0\) and \(x_0\) such that

$$c\,g(x)\le f(x) \qquad \text{for all } x\ge x_0.$$

Definition 3 — Big-Θ (bounded both ways)

If \(f(x)\in O(g(x))\) and \(f(x)\in\Omega(g(x))\), then \(f(x)\in\Theta(g(x))\) — read "theta" — meaning \(f(x)\) and \(g(x)\) have the same time complexity (the same growth rate, up to constants).

Worked proof — show that \(\dfrac{n(n-1)}{2}\in\Theta(n^2)\)

Let \(f(n)=\dfrac{n(n-1)}{2}\) and \(g(n)=n^2\).

Part 1 — show \(f(n)\in O(g(n))\). We need \(f(n)\le c\,g(n)\) for some \(c>0\):

$$f(n) = \frac{n(n-1)}{2} = \frac{n^2}{2}-\frac{n}{2} \;\le\; \frac{n^2}{2} = c\,g(n), \quad \text{where } c=\frac12$$

(the inequality holds because we're only removing the non-negative quantity \(\frac{n}{2}\), which can only make the left side smaller — "at most" \(\frac{n^2}{2}\)). This holds for all \(n\ge n_0=1\) — i.e. for every natural number — so

$$f(n)\in O(n^2) \qquad \text{—— (1)}$$

Part 2 — show \(f(n)\in\Omega(g(n))\). We need \(c\,g(n)\le f(n)\) for some \(c>0\) and all \(n\ge n_0\):

$$f(n) = \frac{n^2}{2}-\frac{n}{2}\cdot 1 \;\ge\; \frac{n^2}{2}-\frac{n}{2}\cdot\frac{n}{2}, \quad \text{take } n\ge 2$$

This step substitutes \(1\) with \(\dfrac{n}{2}\) in the subtracted term — valid because \(n\ge2\) means \(\dfrac{n}{2}\ge1\), and substituting a larger value into a term being subtracted can only make the whole expression smaller or equal, so the inequality direction is preserved. Simplifying the right-hand side:

$$= \frac{n^2}{2}-\frac{n^2}{4} = \frac{n^2}{4} = c\cdot g(n), \quad \text{where } c=\frac14$$

So choosing \(n_0=2\) and \(c=\frac14\) makes \(f(n)\ge c\,g(n)\) true for every \(n\ge n_0\). So:

$$f(n)\in\Omega(n^2) \qquad \text{—— (2)}$$

Conclusion. By (1) and (2) together:

$$f(n) = \frac{n(n-1)}{2} \in \Theta(n^2)$$

∎   Bubble Sort has quadratic growth.

Common confusion — the constants aren't unique

Notice \(c=\frac12\) worked for the Big-O half and \(c=\frac14\) worked for the Big-Ω half — these don't need to match, and in fact the choice of \(c\) and \(n_0\) is never unique. Definitions 1 and 2 only ask that some valid choice exists — there's flexibility of choice allowed for equal numbers (i.e. many different \((c,n_0)\) pairs can all correctly witness the same bound). Proving a bound means exhibiting one working choice, not finding "the" choice.

Homework left in the lecture — and its solution, shown above

The lecture actually poses this as homework at the end of L1: prove \(f(n)\in\Omega(g(n))\) where \(f(n)=\dfrac{n^2}{2}-\dfrac{n}{2}\), \(g(n)=n^2\) — find explicit constants \(c\) and \(n_0\) such that \(f(n)\ge c\,n^2\) for all \(n\ge n_0\). The worked proof above is that solution — it's exactly what Lecture 2 opens with, confirming \(c=\frac14,\,n_0=2\) work, before moving on to new material.

Where Lecture 1 leaves us

Algorithms must be correct and must terminate in finite time. We measure them by counting operations as a function of input size \(n\) — this is time (and space) complexity. Big-O, Big-Ω, and Big-Θ give us a rigorous, hardware-independent language for describing that growth, and Bubble Sort is our first example: it makes \(\Theta(n^2)\) comparisons and \(\Theta(n^2)\) exchanges in the worst case.

Lecture 2

Growth Rates — Why Exponential Is a Different World

This lecture finishes off Lecture 1's homework, then builds a complete mental map of every growth rate you'll meet in this course — from \(\log n\) up to \(n^n\) — using one simple technique (limits) to compare any two of them. It closes with a formal, line-by-line pseudocode for Bubble Sort and a rigorous derivation of its time complexity.

2.1 · Finishing Lecture 1's homework

Recall the task: show \(f(n)=\dfrac{n^2}{2}-\dfrac{n}{2}\in\Omega(n^2)\), i.e. find \(c>0\) and \(n_0\) with \(f(n)\ge c\,n^2\) for all \(n\ge n_0\).

Proof

Start from \(f(n)\) and, for \(n\ge2\), replace the "\(1\)" being subtracted with the larger quantity \(\dfrac{n}{2}\) (valid since \(n\ge2\Rightarrow\dfrac{n}{2}\ge1\), and substituting a larger value into a subtracted term can only shrink the whole expression, preserving the \(\ge\)):

$$f(n) = \frac{n^2}{2}-\frac{n}{2}\cdot1 \;\ge\; \frac{n^2}{2}-\frac{n}{2}\cdot\frac{n}{2} = \frac{n^2}{2}-\frac{n^2}{4} = \frac{n^2}{4}$$

So \(f(n)\ge\dfrac14n^2\) for every \(n\ge2\) — take \(c=\dfrac14\), \(n_0=2\). Hence \(f(n)\in\Omega(n^2)\), and combined with Lecture 1's \(O(n^2)\) result:

$$f(n)\in\Theta(n^2)$$

∎  Bubble Sort has quadratic growth — confirmed.

2.2 · A map of every growth rate

Lay out the growth rates you'll meet, slowest to fastest:

\(\log n\)  |  \(\sqrt n\)  |  \(n\)  |  \(\log n! \equiv n\log n\)  |  \(n^2\)  |  \(n^3\)  |  \(\cdots\)  |  \(2^n\)  |  \(n!\)  |  \(n^n\)
CategoryMembers

Linear\(n\)
Polynomial\(n\log n\), \(n^2\), \(n^3\), ...

The technique: compare via a limit

The comparison rule

To decide whether \(f(n)\le g(n)\) asymptotically, compute \(\displaystyle\lim_{n\to\infty}\frac{f(n)}{g(n)}\). If this limit is \(0\), then \(f(n)\) is eventually dominated by \(g(n)\).

Worked example — confirm \(n^2\le n^3\)

$$\lim_{n\to\infty}\frac{n^2}{n^3} = \lim_{n\to\infty}\frac1n = 0 \quad\Longrightarrow\quad n^2\le n^3$$

The same trivial argument gives \(\sqrt n\le n\), since \(\sqrt n\cdot1\le\sqrt n\cdot\sqrt n=n\).

Proof — \(\log n \le \sqrt n\)

Compute \(\displaystyle\lim_{n\to\infty}\frac{\log n}{\sqrt n}\), an \(\frac{\infty}{\infty}\) form — apply L'Hôpital's rule (differentiate top and bottom; assume \(\log\) is natural log throughout):

$$\lim_{n\to\infty}\frac{\log n}{\sqrt n} = \lim_{n\to\infty}\frac{1/n}{\frac12 n^{-1/2}} = \lim_{n\to\infty}\ 2\cdot\frac1n\cdot\sqrt n = \lim_{n\to\infty}\frac{2}{\sqrt n} = 0$$

So \(\log n\le\sqrt n\).

∎

Where does exponential growth actually come from? Recall Tower of Hanoi

Recall — Tower of Hanoi, previewed

Tower of Hanoi with \(n\) disks takes \(2^n-1\) steps (this count is derived properly from a recurrence in Lecture 4 — for now, just take it as a known fact worth comparing against). Since \(2\le n\) for \(n\ge2\), trivially \(2^n\le n^n\). But how does \(2^n\) compare to \(n!\), and to \(n^n\)?

Proof — \(n! \le n^n\)

$$n! = n\times(n-1)\times\cdots\times2\times1 \;\le\; n\times n\times\cdots\times n = n^n$$

(every one of the \(n\) factors in \(n!\) is at most \(n\)). So \(n!\le n^n\).

∎

Proof — \(2^n \le n!\) (eventually)

We first need a lower bound on \(\log(n!)\). Here's a clean way to get one: drop the smaller half of the factors in \(n!\), keeping only the larger ones, each of which is at least \(\dfrac n2\):

$$n! = 1\cdot2\cdots\Big(\frac n2\Big)\Big(\frac n2+1\Big)\cdots n \;\ge\; \Big(\frac n2\Big)\Big(\frac n2\Big)\cdots\Big(\frac n2\Big) = \Big(\frac n2\Big)^{n/2}$$

(there are \(n/2\) surviving factors, and every one of them has been shrunk down to exactly \(n/2\), so the product can only have gotten smaller — the inequality direction is safe). Taking logs:

$$\log(n!) \ge \frac n2\log\frac n2 \qquad\text{—— (a lower bound we'll reuse in Lecture 3)}$$

Now compare \(2^n\) against \(n!\) via the same limit technique, using \(\log(n!)\approx n\log n\) as a stand-in for the denominator's growth:

$$\lim_{n\to\infty}\frac{n\log2}{\log(n!)} = \lim_{n\to\infty}\frac{n\log2}{n\log n} = \lim_{n\to\infty}\frac{\log2}{\log n} = 0$$

Since the ratio of the logs of \(2^n\) and \(n!\) goes to 0, \(2^n\) is eventually dominated by \(n!\):

$$2^n \le n!$$

∎

Common confusion — why compare the logs at all?

Comparing \(\log(2^n)\) against \(\log(n!)\) instead of comparing \(2^n\) and \(n!\) directly is just a convenience: logs turn the unwieldy factorial and exponential into more manageable expressions (\(n\log2\) and roughly \(n\log n\)) without changing which one is bigger — \(\log\) is an increasing function, so it preserves order. This is the exact same reason logs show up constantly throughout this topic.

Putting real numbers to the growth-rate table

Look at the jump from \(n^3=10^6\) to \(2^n\approx1.27\times10^{30}\) — that's not a bigger number in the way \(10^6\) is bigger than \(10^3\); it's a difference in kind. This is exactly why the boundary between polynomial and exponential matters so much in this field: it's the boundary between "solvable in practice" and "not solvable in practice," no matter how fast computers get.

Worked example — how long would 100-disk Tower of Hanoi actually take?

Suppose a computer can perform \(10^{12}\) operations per second (a very generous estimate — a typical single CPU core runs at roughly 2.44 GHz, i.e. about \(2.44\times10^9\) cycles per second). Tower of Hanoi with 100 disks takes \(2^{100}-1\approx2^{100}\) steps. How long does that take?

$$\frac{2^{100}}{10^{12}}\text{ seconds} = \frac{2^{100}}{60\times10^{12}}\text{ minutes} = \frac{1.27\times10^{30}}{60\times60\times10^{12}}\text{ hours}$$

$$= \frac{1.27\times10^{30}}{60\times60\times24\times10^{12}}\text{ days} = \frac{1.27\times10^{30}}{365\times60\times60\times24\times10^{12}}\text{ years}$$

Result

$$\approx 4.03\times10^{10}\text{ years}$$

A computer performing a trillion operations every second would still need about 40 billion years to finish — roughly nine times the age of the Earth (\(4.5\times10^9\) years, or 4.5 billion years). This is the real, physical meaning of "exponential time": no realistic amount of hardware speed rescues you from it.

2.3 · Bubble Sort, written as formal pseudocode

Having built the language of growth rates, return to Bubble Sort and write it precisely — array-indexed, ready to analyse line by line.

Input & setup

Input: an array of \(n\) elements, \(A[1,\dots,n]\). Number of (outer) steps involved: \(n-1\).

1  for i ← 1 to n-1
2      for j ← 1 to n-i
3          if A[j+1] < A[j] then
4              A[j+1] ↔ A[j]     // swap — this comparison is the basic operation
Verifying the loop bounds don't overrun the array

It's worth checking this carefully rather than trusting it by eye. When \(i=1\), the inner loop runs \(j=1\) to \(n-1\), and the largest index touched is \(A[j+1]\) at \(j=n-1\), i.e. \(A[n]\) — exactly the last valid index, not one past it. So the bound \(j\le n-i\) is exactly right, not off by one.

Concrete check from the running example: with \(A=[\dots,7,25,\dots]\), the test "\(25 < 10\)?" is false (nothing happens), while "\(7 < 25\)?" is true, triggering a swap — exactly matching the algorithm's line 3–4 logic.

Deriving the time complexity from the pseudocode directly

Calculating time complexity / number of comparisons

Each pass of the inner loop performs exactly one comparison, so counting comparisons means counting how many times the inner loop body runs, summed over every outer iteration — a double sum (the worst case is taken, since every comparison happens regardless of the data):

$$T(n) = \sum_{i=1}^{n-1}\sum_{j=1}^{n-i} 1 = \sum_{i=1}^{n-1}(n-i) = (n-1)+(n-2)+\cdots+1 = \frac{n(n-1)}{2} \in \Theta(n^2)$$

∎

Two questions left open, for you to think about
  • What about the number of exchanges (not comparisons)? In the worst case, this is also \(\Theta(n^2)\) — can you see why, from the pseudocode?
  • Can you make the number of exchanges linear, \(\Theta(n)\), with a small modification to the algorithm? (Think about what information you'd need to track instead of swapping immediately.)
Where Lecture 2 leaves us

Every growth rate you'll meet in this course can be placed on one scale — sub-linear, linear, polynomial, exponential — and any two can be compared with a single limit computation. Exponential growth (\(2^n\), \(n!\), \(n^n\)) isn't just "big," it's a different category of big, one that stays out of reach no matter how fast computers get. And Bubble Sort's \(\Theta(n^2)\) time complexity, guessed informally in Lecture 1, now has a fully rigorous derivation straight from its pseudocode.

Lecture 3

Selection Sort, and Proving a Lower Bound Is Actually a Lower Bound

This lecture completes the \(\log(n!)\in\Theta(n\log n)\) result in full rigor, introduces Selection Sort as an algorithm that fixes one of Bubble Sort's weaknesses, and then does something new: it doesn't just find an algorithm's running time, it proves no algorithm could possibly do better — using a genuinely beautiful graph-theoretic argument.

3.1 · \(\log(n!)\in\Theta(n\log n)\), the complete proof

Recall the growth-rate line from Lecture 2 placed \(n\log n\) and \(\log(n!)\) at the same point. Here is the full, careful proof of that claim, revisiting the pairing technique from Lecture 2 more rigorously.

Proof — the lower bound, \(\log(n!)\in\Omega(n\log n)\)

Expand \(\log(n!)\) as a sum, then pair the terms from the outside in — first with last, second with second-last, and so on:

$$\log n! = \log\big(n\cdot(n-1)\cdots2\cdot1\big) = \log n+\log(n-1)+\cdots+\log2+\log1$$

$$= \big(\log n+\log1\big)+\big(\log(n-1)+\log2\big)+\cdots+\left(\log\frac n2+\log\Big(\frac n2-1\Big)\right)$$

Every single pair-sum here is at least \(\log\dfrac n2+\log\dfrac n2\)... actually, more simply, each individual term in every pair is at least \(\log\frac{n}{2}\) once we're past the halfway point, so bounding every pair below by \(2\log\frac{n}{2}\) and summing across the \(n/2\) pairs:

$$\log n! \;>\; \underbrace{\log\frac n2+\log\frac n2+\cdots+\log\frac n2}_{n/2\text{ copies}} \;=\; \frac n2\log\frac n2$$

Now expand and split this bound to isolate a clean \(n\log n\) term:

$$\frac n2\log\frac n2 = \frac n2\log n-\frac n2\log2 = \left(\frac n4\log n+\frac n4\log n\right)-\frac n2\log2 = \frac n4\log n + n\left(\frac14\log n-\frac12\log2\right)$$

When does the bracketed term become non-negative? We need \(\frac14\log n-\frac12\log2\ge0\):

$$\frac14\log n\ge\frac12\log2 \;\Longleftrightarrow\; \log n\ge2\log2=\log4 \;\Longleftrightarrow\; n\ge4$$

So, choosing \(n_0=4\), the bracketed term is \(\ge0\) for all \(n\ge n_0\), which means:

$$\log n! \;\ge\; \frac n4\log n \qquad\text{for all } n\ge4$$

Take \(c=\dfrac14\), \(n_0=4\): this proves \(\log n!\in\Omega(n\log n)\).

∎  — (result 1)

Proof — the upper bound, \(\log(n!)\in O(n\log n)\)

This direction is much shorter. Every one of the \(n\) factors in \(n!\) is at most \(n\):

$$n! = n\cdot(n-1)\cdots2\cdot1 \;\le\; \underbrace{n\cdot n\cdots n}_{n\text{ times}} = n^n$$

Taking logs of both sides (log is increasing, so the inequality direction is preserved):

$$\log n! \le \log(n^n) = n\log n$$

This holds with \(c=1\) for every \(n\ge1\) — no threshold needed at all. So \(\log n!\in O(n\log n)\).

∎  — (result 2)

Key result

By results 1 and 2 together:

$$\log(n!) \in \Theta(n\log n)$$

A useful shortcut for future comparisons — the limit test, summarised

Lecture 2's limit technique generalises into one clean rule you can reuse for the rest of the course. To compare \(f(n)\) against \(g(n)\), compute \(\displaystyle\lim_{n\to\infty}\frac{f(n)}{g(n)}\):

  • If the limit is \(0\), then \(f(n) < g(n)\) asymptotically, so \(f(n)\in O(g(n))\).
  • If the limit is a finite, nonzero constant \(k\), then \(f(n)\) and \(g(n)\) grow at the same rate, so \(f(n)\in\Theta(g(n))\).
  • If the limit is \(\infty\), then \(f(n)>g(n)\) asymptotically, so \(f(n)\in\Omega(g(n))\).
Worked example — a quick check that \(n-1\in\Theta(n)\)

$$\lim_{n\to\infty}\frac{n-1}{n} = \lim_{n\to\infty}\left(1-\frac1n\right) = 1\ne0 \quad\Longrightarrow\quad n-1\in\Theta(n)$$

Worth having in your pocket: this exact fact — that "\(n-1\)" and "\(n\)" have the same order of growth — quietly justifies writing \(\Theta(n)\) instead of the more cumbersome \(\Theta(n-1)\) whenever an algorithm's count comes out to something like \(n-1\).

3.2 · Selection Sort

Bubble Sort's real weakness isn't its comparison count — Selection Sort will match it exactly — it's the number of swaps, which can be as bad as \(\Theta(n^2)\) in the worst case. Selection Sort fixes this by deciding on one swap per pass, no matter what.

Analysis: comparisons and swaps

Number of comparisons

The comparison on line 4 runs once per inner-loop iteration — a double sum, exactly like Bubble Sort's:

$$T(n) = \sum_{i=1}^{n-1}\sum_{j=1}^{n-i}1 = \sum_{i=1}^{n-1}(n-i) = (n-1)+(n-2)+\cdots+1 = \frac{n(n-1)}2 \in\Theta(n^2)$$

∎

Number of swaps

Exactly one swap (line 5) happens per outer-loop pass, and there are \(n-1\) passes:

$$S(n) = \sum_{i=1}^{n-1}1 = n-1 \in\Theta(n)$$

∎  This directly answers Lecture 2's open question: yes, the number of swaps can be made linear.

3.3 · Finding the maximum: a genuine lower-bound proof

Every algorithm so far has come with an upper bound on its running time — "this algorithm takes at most this much time." This section asks a fundamentally different question: is it possible to prove that no algorithm, however cleverly designed, could ever do better?

Result — the claim to be proved

Finding the maximum (or minimum) in an array of size \(n\) takes \(n-1\) comparisons.

First, an algorithm that achieves n − 1

Code to find the max

Input: \(A[1,2,\dots,n]\).

1  pos ← 1
2  for i ← 2 to n
3      if A[pos] < A[i] then pos ← i
4  print A[pos]

The loop runs once for every \(i=2,\dots,n\), making one comparison each time:

$$T(n) = \sum_{i=2}^{n}1 = n-1 \in\Theta(n)$$

So an algorithm exists using exactly \(n-1\) comparisons. That settles the upper bound. The much harder, more interesting question: could some other, cleverer algorithm possibly do it in fewer?

Now, the lower bound: no algorithm can do better

Proof by contradiction

Suppose, for contradiction, that some algorithm \(A\) exists which finds the maximum using fewer than \(n-1\) comparisons. We will show that \(A\) must then be incorrect on some input — contradicting the assumption that \(A\) correctly finds the maximum.

Step 1 — build a graph from \(A\)'s comparisons. Create a graph \(G\) with one vertex per array element. Every time algorithm \(A\) compares \(A[i]\) with \(A[j]\), draw an edge connecting those two vertices.

Step 2 — too few comparisons means a disconnected graph. Recall: a tree on \(n\) vertices has exactly \(n-1\) edges and is connected with no cycles — the minimally connected graph on \(n\) vertices. If \(G\) has fewer than \(n-1\) edges (because \(A\) made fewer than \(n-1\) comparisons), \(G\) cannot be a tree, and in particular cannot be connected. So \(G\) splits into at least two disconnected components, call them \(C_1\) and \(C_2\).

Step 3 — the true maximum lives in one component. The maximum value \(M\) of the whole array sits at some vertex, which must belong to either \(C_1\) or \(C_2\). Without loss of generality, say \(M\) is in \(C_1\).

Step 4 — the adversarial trick. Since \(A\) never once compared any element of \(C_1\) with any element of \(C_2\) (there are no edges between the two components), algorithm \(A\)'s entire sequence of decisions — every comparison outcome — depends only on the elements within each component, never on any relationship between them. Now construct a new input: take the original array, and add \(M\) to every element in \(C_2\), leaving \(C_1\) untouched, and feed this as the input to \(A\).

Concrete numeric illustration

Suppose \(C_1=\{15,25,16,4\}\) (so \(M=25\)) and \(C_2=\{2,6,5,14,1\}\). Add \(M=25\) to every element of \(C_2\), giving \(C_2'=\{27,31,30,39,26\}\). The true maximum of this new array is now \(39\) — but algorithm \(A\), having made exactly the same comparisons as before (none of them touching \(C_2\)), still outputs \(M=25\).

Step 5 — contradiction. Since \(A\) makes no comparisons involving \(C_2\), its behaviour — and therefore its output — is identical to what it was on the original input: it still reports \(M\) as the maximum. But the actual maximum of the new array is now some element of \(C_2'\) (strictly greater than \(M\), since every element of \(C_2\) was some positive-contributing value before \(M\) was added to it). So \(A\) outputs the wrong answer on this input.

This contradicts our assumption that \(A\) is a correct algorithm for finding the maximum. Hence, no algorithm using fewer than \(n-1\) comparisons can correctly find the maximum of every input.

∎

Key result — a tight algorithm

Since an algorithm achieving exactly \(n-1\) comparisons exists (the upper bound), and no algorithm can do it in fewer than \(n-1\) (the lower bound just proved), finding the max/min in an array is settled completely:

$$\Theta(n) \text{ comparisons — and this is optimal, not just achievable.}$$

Why this proof technique matters beyond this one problem

This is your first example of a genuine lower-bound proof — a proof that no clever trick, no matter how sophisticated, can beat a certain running time. Notice the strategy: assume a better algorithm exists, build a structure (here, a graph) from its behaviour, and then construct an adversarial input that exploits a gap in that structure to force a wrong answer. This exact style of argument — build a comparison graph, exploit disconnection — reappears in a much bigger way in Lecture 8, to prove that no comparison-based sorting algorithm can beat \(\Omega(n\log n)\).

Lecture 4

Tower of Hanoi — Deriving Exponential Growth From Scratch

Lecture 2 asked you to simply recall that Tower of Hanoi takes \(2^n-1\) steps. This lecture proves it — building the recurrence relation from the puzzle's actual structure, solving it completely by unrolling, and then confirming just how real "exponential time" is with a concrete timing estimate.

4.1 · The puzzle, its rules, and small cases

Setup

Tower of Hanoi consists of 3 pegs (A, B, C) and \(n\) disks of different sizes, all initially stacked on peg A in decreasing order of size (largest at the bottom).

Rules
  1. Move one disk at a time.
  2. Never place a larger disk onto a smaller one ("no bullying").

Question: can you move all \(n\) disks from Tower A to Tower B (using Tower C as a spare), obeying both rules? And if so — how many moves does it take, at minimum?

Building intuition from the smallest cases

n = 1 disk

Trivial: move the single disk directly from A to B. 1 step.

n = 2 disks

Question first: can it be done in fewer than 3 steps? As there are \(n=2\) disks, at least 2 moves are required just to relocate them — but check: can it be done in exactly 2? Attempting it shows no arrangement of 2 moves obeys rule 2 while finishing the job. It takes exactly 3 steps: move the small disk A→C, the large disk A→B, then the small disk C→B. 3 is the optimum number of moves for \(n=2\). (Note: none of the pegs are allowed to have any disks on them initially besides Tower A's full stack — the other two start empty.)

n = 3 disks

Working it through by hand, disk by disk, takes exactly 7 steps.

4.2 · The recurrence, derived and solved

Rather than guess-and-check for every \(n\), notice the structure hiding in the \(n=3\) solution. Moving 3 disks from A to B breaks cleanly into three phases:

  1. Move the top \(n-1\) disks from A to the spare peg C (ignoring the bottom disk entirely) — this is itself a Tower-of-Hanoi problem of size \(n-1\), taking \(T(n-1)\) steps.
  2. Move the single largest disk from A to B — 1 step.
  3. Move the \(n-1\) disks now sitting on C over to B, on top of the largest disk — again a size-\((n-1)\) sub-problem, taking \(T(n-1)\) steps.

Steps 5–7 of the \(n=3\) solve, for instance, are exactly phase 3: the two smaller disks, sitting on the spare peg, get moved on top of the (already-placed) largest disk — a symmetric mirror of phase 1.

The recurrence for Tower of Hanoi

Phases 1 and 3 are symmetric — both are the identical sub-problem of moving \(n-1\) disks, so both cost exactly \(T(n-1)\):

$$T(n) = T(n-1)+1+T(n-1) = 2T(n-1)+1, \qquad T(1)=1$$

Solving the recurrence, by unrolling

Substitute the recurrence into itself, repeatedly, tracking the pattern:

$$T(n) = 2T(n-1)+1$$

$$= 2\big\{2T(n-2)+1\big\}+1 = 2^2T(n-2)+2+1$$

$$= 2^2\big\{2T(n-3)+1\big\}+2+1 = 2^3T(n-3)+2^2+2+1$$

The pattern emerging: after \(k\) substitutions, \(T(n)=2^kT(n-k)+2^{k-1}+\cdots+2+1\). Push this all the way to \(k=n-1\), where the recursion bottoms out at the known base case \(T(1)=1\):

$$T(n) = 2^{n-1}T\big(n-(n-1)\big)+2^{n-2}+2^{n-3}+\cdots+2+1 = 2^{n-1}T(1)+2^{n-2}+\cdots+2+1$$

$$= 2^{n-1}+2^{n-2}+2^{n-3}+\cdots+2+1$$

This is a geometric series with first term \(a=1\) and common ratio \(r=2\), summed to \(n\) terms:

$$T(n) = \frac{2^n-1}{2-1} = 2^n-1$$

∎

Confirming \(2^n-1\in\Theta(2^n)\)

Using the limit technique from Lectures 2–3:

$$\lim_{n\to\infty}\frac{2^n-1}{2^n} = \lim_{n\to\infty}\left(1-\frac1{2^n}\right) = 1 \ne 0 \quad\Longrightarrow\quad 2^n-1\in\Theta(2^n)$$

∎

Key result

Tower of Hanoi with \(n\) disks requires exactly \(2^n-1\) moves — an exponential-time problem, now fully derived rather than merely observed.

4.3 · How long would 100 disks really take?

The lecture revisits exactly the timing calculation from Lecture 2, now that \(2^n-1\) is a proven fact rather than a recalled one. Assume a computer performing \(10^{12}\) operations/second, and \(n=100\) disks, needing \(2^{100}-1\approx2^{100}\) operations:

$$\frac{2^{100}}{10^{12}} = 1.29\times10^{18}\text{ seconds} = 2.1\times10^{16}\text{ minutes} = 3.5\times10^{14}\text{ hours} = 1.4\times10^{13}\text{ days}$$

Result

$$\frac{1.4\times10^{13}}{365}\text{ years} \approx 4.0\times10^{10}\text{ years}$$

Compare this to the age of the Earth: \(4.5\times10^9\) years (4.5 billion years). A 100-disk Tower of Hanoi would take roughly nine Earth-lifetimes to finish, even at a trillion operations per second — the exact same conclusion reached in Lecture 2, now backed by a fully derived formula rather than an assumed one.

Note — exponential algorithms aren't always useless
  • Exponential algorithms are actually useful in cryptography and encryption — there, you often want a problem to be prohibitively expensive to solve without the right key (see the RSA algorithm, previewed in this course's syllabus).
  • For other purposes, exponential algorithms may only be practical for small cases of \(n\) — exactly what the 100-disk calculation above illustrates.

Lecture 5

Merge Sort — Breaking Θ(n²)

Every algorithm so far has been quadratic. This lecture finally breaks that barrier: first by showing that merging two already-sorted arrays takes only linear time, then by building an entire sorting algorithm — Merge Sort — around that one fast operation, and proving its running time is \(\Theta(n\log n)\) two completely different ways.

5.1 · Merging two sorted arrays

Result

Merging two already-sorted arrays into a single sorted array takes linear time.

Merge — pseudocode

Input: two sorted arrays \(A[1,\dots,p]\) and \(B[1,\dots,q]\); output: \(C[1,\dots,p+q]\).

1  i ← 1,  j ← 1,  k ← 1
2  while i ≤ p and j ≤ q
3      if A[i] ≤ B[j]
4          C[k] ← A[i];  i ← i+1        // basic operation: the comparison
5      else
6          C[k] ← B[j];  j ← j+1
7      k ← k+1
8  if i = p+1 then copy B[j…q] to C[k…p+q]     // A ran out first
9  if j = q+1 then copy A[i…p] to C[k…p+q]     // B ran out first
Worked example

\(A=[2,7,11]\) (\(p=3\)), \(B=[5,9]\) (\(q=2\)). Trace the merge:

Result: \(C=[2,5,7,9,11]\), using just 4 comparisons — one fewer than the 5 total elements, because the very last element never needs comparing; once one array is exhausted, the rest of the other array is simply copied over.

Analysis — number of comparisons

Every value of \(k\) involves exactly one comparison, except the very last, \((p+q)\)-th value (which is handled by the copy-the-remainder steps, lines 8–9, with no comparison needed):

$$\text{Total comparisons} = p+q-1$$

Setting \(p=q=n\) (merging two equal-sized halves, as Merge Sort will do):

$$T(n) = 2n-1 \in \Theta(n)$$

∎  Merging is linear — the key fact the rest of this lecture is built on.

5.2 · Merge Sort, and its recurrence

The idea: split the array in half, recursively sort each half, then merge the two sorted halves together using the fast linear-time merge above. Split \([7,17,12,5,1,6,4]\) all the way down to single elements (each trivially "sorted"), then merge pairs back up.

Merge Sort — pseudocode 
1  MergeSort(A[1…n])
2      if n > 1
3          copy A[1…⌊n/2⌋-1] to B[1…⌊n/2⌋-1]
4          copy A[⌊n/2⌋…n] to C[1…⌈n/2⌉-1]
5          MergeSort(B[1…⌊n/2⌋-1])
6          MergeSort(C[1…⌈n/2⌉-1])
7          Merge(B, C, A)

Sort \([7,17,12,5,1,6,4]\) (odd-sized, so one element sits out a level):

The recurrence for Merge Sort

"These divide-and-conquer algorithms are often analysed using recurrence relations."

$$T(n) = \begin{cases}\Theta(1) & n=1\\[4pt] 2T(n/2)+\Theta(n) & n>1\end{cases}$$

Each recursive call gets a problem of half the size ("each time we get 2 problems, each half the size of the initial one"), and the \(\Theta(n)\) term is exactly the linear merging time just proved above.

5.3 · Solving the recurrence, two different ways

Method 1 — solving by unrolling

Write \(T(n)=2T(n/2)+cn\), and substitute the recurrence into itself repeatedly:

$$T(n) = 2T\Big(\frac n2\Big)+cn = 2\left(2T\Big(\frac n4\Big)+\frac{cn}2\right)+cn = 2^2T\Big(\frac n4\Big)+cn+cn$$

$$= 2^2\left(2T\Big(\frac n8\Big)+\frac{cn}4\right)+cn+cn = 2^3T\Big(\frac n8\Big)+cn+cn+cn = 2^3T\Big(\frac n8\Big)+c(3n)$$

The pattern: after \(x\) substitutions, \(T(n)=2^xT(n/2^x)+c(xn)\). This bottoms out once \(n/2^x=1\), i.e. \(x=\log_2n\):

$$T(n) = 2^{\log_2n}T(1) + c(\log n)\,n = n\cdot T(1) + cn\log n = n + c(n\log n)$$

Since \(n\log n\) dominates the lone \(n\) term (\(n\log n\) is greater than \(n\) for \(n>1\)):

$$T(n)\in O(n\log n)$$

∎

Method 2 — solving via the recursion tree

Draw the recursion as a tree: the root does \(cn\) work (the merge at the top level), splitting into two children each doing \(c\cdot\frac n2\) work, splitting again into four children each doing \(c\cdot\frac n4\), and so on, down to leaves \(T(1)\).

Key observation: the horizontal sum at every level is exactly \(cn\) — each level has twice as many nodes as the one above, but each node does half the work, so the products cancel and every level contributes the same total, \(cn\).

So \(T(n) = h\cdot(cn)\), where \(h\) is the height of the tree. Now find \(h\): a binary tree of height \(h\) has at most \(2^h\) leaves (check small cases: \(h=0\to1=2^0\) leaf, \(h=1\to2=2^1\) leaves, \(h=2\to4=2^2\) leaves — doubling at each level, confirming \(2^h\) by induction). Since the input has \(n\) elements, and in Merge Sort every input element must eventually become its own leaf (a single sorted number), we need enough leaves to cover all of them:

$$2^h \ge n \;\Longrightarrow\; \log(2^h)\ge\log n \;\Longrightarrow\; h\ge\log n \quad(\text{log is monotonic, so the inequality survives})$$

Take \(h=\lceil\log n\rceil\). Substituting back:

$$T(n) = \lceil\log n\rceil\cdot cn \in O(n\log n)$$

∎  Two independent methods, same answer — good evidence the result is right.

Key result

Merge Sort runs in \(\Theta(n\log n)\) time — a genuine improvement over Bubble Sort and Selection Sort's \(\Theta(n^2)\). For large \(n\), this is the difference between "usable" and "not usable," exactly as the growth-rate table from Lecture 2 would predict.

5.4 · A puzzle to end on: the decision-tree model

Having found an algorithm that sorts in \(\Theta(n\log n)\), a natural question follows: could something even faster exist? The lecture poses a puzzle, to be fully resolved in Lecture 8: model every comparison-based sorting algorithm as a decision tree.

A puzzle — sorting three elements as a decision tree

To sort \(\langle a_1,a_2,a_3\rangle\), the first comparison might be "\(a_1\) vs \(a_2\)?" Depending on the outcome, a different second comparison follows, and so on — each internal node of the tree is a comparison, and each leaf is a fully determined sorted order (a permutation of the input), such as \(a_1a_2a_3\), \(a_2a_1a_3\), \(a_2a_3a_1\), \(a_3a_2a_1\), etc.

(This is exactly the question Lecture 8 answers in full, and it leads to a genuine lower bound — just like Lecture 3's max-finding proof — for every comparison-based sorting algorithm that could ever be written.)

Lecture 6

Quicksort — Sorting Without Auxiliary Arrays

Merge Sort reaches \(\Theta(n\log n)\), but it pays for that speed with extra memory — two auxiliary arrays, \(B\) and \(C\), at every level of recursion. This lecture asks: can the same \(\Theta(n\log n)\) speed be reached in place, using no extra arrays at all? The answer is Quicksort, built around one clever subroutine: Partition.

6.1 · Partitioning in place

The motivating question

Can you sort in \(\Theta(n\log n)\) time without using auxiliary arrays? Yes — using divide-and-conquer, but with no auxiliary arrays at all.

The core idea: pick a pivot (here, always the first element), then rearrange the array so that every element \(\le\) the pivot ends up on its left, and every element \(>\) the pivot ends up on its right — with the pivot itself dropped into its final, correct sorted position, right at the boundary. This is called putting the pivot "in its proper place."

Partition — pseudocode (Hoare/Lomuto-style, 1962)

Input: \(A[p,\dots,q]\); rearranges \(A\) in place and returns the pivot's final index.

1  Partition(A, p, q)
2      x ← A[p]                       // pivot
3      i ← p
4      for j ← p+1 to q
5          if A[j] ≤ x
6              i ← i+1
7              A[i] ↔ A[j]
8      A[p] ↔ A[i]                   // drop the pivot into its final place
9      return i
Worked example — Partition(A, 1, 8)

Partition's running time

The loop runs once for every \(j=p+1,\dots,q\) — a single pass:

$$T(n) = \sum_{i=1}^{n}1 = n \in \Theta(n)$$

∎  Partitioning is linear — and crucially, it uses no auxiliary array; every rearrangement happens inside A itself.

6.2 · Quicksort itself

Quicksort — pseudocode 
1  Quicksort(A, p, q)
2      if p < q
3          then r ← Partition(A, p, q)
4          Quicksort(A, p, r-1)
5          Quicksort(A, r+1, q)

Initial call: Quicksort(A, 1, n).

Partition does all the real work of placing one element correctly; Quicksort's job is simply to call Partition, then recurse on the two pieces that result — left of the pivot, and right of the pivot. Unlike Merge Sort, there's no separate "merge" step at the end: once every element has been placed by some call to Partition, the array is already fully sorted.

6.3 · Worst-case analysis: Θ(n²)

Worst-case input

Give Quicksort an already-sorted array (ascending or descending order). Since the pivot is always the first element, and the array is already ordered, every Partition call splits the array as unevenly as possible: one side gets everything, the other side gets nothing.

Illustration

\(A=[10,8,7,5,4,3]\): pivot 10 is already the maximum, so Partition places it correctly at the very last position with everything else ending up on the left — the split is \((n-1, 0)\), the most unbalanced possible.

Solving the worst-case recurrence

With a \((n-1,0)\) split every time, plus \(\Theta(n)\) partitioning work, plus the (trivial, \(\Theta(1)\)) recursive call on the empty side:

$$T(n) = T(n-1)+T(1)+cn$$

Unroll exactly as in earlier lectures:

$$T(n) = T(n-2)+T(1)+c(n-1)+T(1)+cn = T(n-3)+T(1)+c(n-2)+T(1)+c(n-1)+T(1)+cn$$

$$\;\vdots$$

$$= T(1) + \underbrace{(n-1)T(1)}_{n-1\text{ copies of }T(1)} + c\big[n+(n-1)+(n-2)+\cdots+2+1\big]$$

$$= n\cdot T(1) + c\left(\frac{n(n-1)}2\right) \in \Theta(n^2)$$

∎

Key result

Quicksort is quadratic-time under its worst case — exactly as bad as Bubble Sort or Selection Sort, if the input happens to be adversarial (or simply already sorted) and the pivot is always chosen as the first element.

Common confusion — so is Quicksort actually good, or not?

A \(\Theta(n^2)\) worst case sounds damning — but "worst case" means the single most adversarial input, not a typical one. The next lecture asks the more useful question: what happens on a typical input, or even a fairly unbalanced but not maximally-bad one? The answer is the entire reason Quicksort is used constantly in practice despite this worst case.

Lecture 7

Quicksort's Average Case — Why It's Fast in Practice

Lecture 6 ended on a worrying note: Quicksort is \(\Theta(n^2)\) in the worst case. This lecture rebuilds confidence in two stages — first an intuitive stress-test (what if the split is wildly unbalanced, say 10:90?), then a fully rigorous probabilistic analysis using indicator random variables, proving the average running time is \(\Theta(n\log n)\).

7.1 · Recap, and a robustness stress-test

CaseRecurrenceResult
Worst\(T(n)=T(n-1)+T(1)+\Theta(n)\)\(O(n^2)\)
Best\(T(n)=2T(n/2)+\Theta(n)\)\(O(n\log n)\)
Stress test — what if the split is only 10:90, every single time?

Not perfectly balanced (50:50, the best case), and not maximally unbalanced (\((n-1):0\), the worst case) — what if Partition always splits the array into a 10% piece and a 90% piece?

$$T(n) = T\Big(\frac{n}{10}\Big)+T\Big(\frac{9n}{10}\Big)+cn$$

Draw this as a recursion tree. As before, every horizontal level sums to exactly \(cn\) (the same cancellation as Merge Sort's tree). The only difference: the tree is no longer symmetric — the "10%" branch shrinks to size 1 much faster than the "90%" branch does, so the two sides of the tree have different heights:

$$\text{Left height} = \lceil\log_{10}n\rceil \qquad \text{Right height} = \lceil\log_{10/9}n\rceil$$

Since the tree's overall height must accommodate the longer of the two paths, the relevant height is the right side's, \(H=\log_{10/9}n\). By the change-of-base formula, \(\log_{10/9}n\) is just \(\log n\) scaled by the constant \(\dfrac{1}{\log(10/9)}\) — so it's still \(\Theta(\log n)\).

Result

$$T(n) = H\cdot cn \in \Theta(n\log n) \quad\text{— even with a 10:90 split, every single time.}$$

The takeaway

Quicksort doesn't need a perfectly balanced split to achieve \(\Theta(n\log n)\) — even a very lopsided 10:90 split still gives \(\Theta(n\log n)\), because both pieces still shrink geometrically (by a constant factor) at every level. Only a split that leaves one side with a fixed amount of work removed each time (like the worst case's \((n-1):0\) — where the "0" side never grows, and the "\(n-1\)" side only shrinks by exactly 1 each time) breaks this. This is a strong hint that "bad" splits are actually quite rare in a random or typical input — which motivates the fully rigorous average-case analysis that follows.

7.2 · The rigorous average case — indicator random variables

Assume every possible split position is equally likely — i.e. the pivot ends up at each rank with uniform probability \(\dfrac1n\) (this holds, for instance, if the input is a uniformly random permutation, or if the pivot is chosen randomly rather than always as the first element).

Setting up an indicator random variable for each possible split

Define, for \(k=0,1,\dots,n-1\):

$$X_k = \begin{cases}1 & \text{if the } k:(n-k-1) \text{ split occurs}\\0&\text{otherwise}\end{cases}$$

Then the running time itself can be written as a sum over every possible split, weighted by whether that split actually happened:

$$T(n) = \sum_{k=0}^{n-1}X_k\Big(T(k)+T(n-k-1)+\Theta(n)\Big)$$

Step 1 — find \(E[X_k]\)

By the definition of expectation for an indicator variable:

$$E[X_k] = 1\cdot P(k:(n-k-1)\text{ split occurs}) + 0\cdot P(\text{does not occur}) = 1\cdot\frac1n+0\cdot\left(1-\frac1n\right) = \frac1n$$

∎  (using the uniform-split assumption)

Step 2 — take the expectation of the whole recurrence

Apply \(E[\cdot]\) to both sides. Since \(X_k\) is independent of the sub-problem sizes it selects, \(E[X_k\cdot(\cdots)]=E[X_k]\cdot E[\cdots]\):

$$E[T(n)] = \sum_{k=0}^{n-1}E[X_k]\Big(E[T(k)]+E[T(n-k-1)]+\Theta(n)\Big) = \sum_{k=0}^{n-1}\frac1n\Big(E[T(k)]+E[T(n-k-1)]\Big)+\Theta(n)$$

Now, as \(k\) ranges over \(0,1,\dots,n-1\), the quantity \(n-k-1\) also ranges over \(0,1,\dots,n-1\) — just in reverse order. So \(\displaystyle\sum_{k=0}^{n-1}E[T(k)]\) and \(\displaystyle\sum_{k=0}^{n-1}E[T(n-k-1)]\) are the exact same sum, and can be combined:

$$E[T(n)] = \frac2n\sum_{k=0}^{n-1}E[T(k)]+\Theta(n)$$

The plan — prove this by induction

We now have a clean recurrence for \(E[T(n)]\). The claim to prove: \(E[T(n)]=O(n\log n)\). As always with induction on a Big-O claim, this means proving the sharper, constant-explicit statement \(E[T(n)]\le cn\log n\) for a well-chosen \(c\) and all \(n\) past some base case — with the inductive hypothesis assuming the bound already holds for every value less than \(n\). This proof is completed in Lecture 8.

Lecture 8

Finishing the Average-Case Proof, and the Ultimate Sorting Lower Bound

This lecture completes the induction begun in Lecture 7 — using a neat discrete-to-continuous trick (bounding a sum by an integral) — and then delivers the capstone result of the entire sorting unit: a proof that no comparison-based sorting algorithm, ever, can beat \(\Omega(n\log n)\). Merge Sort and randomized Quicksort aren't just fast — they're provably optimal.

8.1 · Finishing the average-case induction

Proof by induction — \(E[T(n)]\le cn\log n\)

Base case. Choose \(c\) large enough that the bound holds trivially for a small base case (e.g. \(n=1\)).

Inductive hypothesis. Assume \(E[T(k)]\le ck\log k\) for every \(k

Inductive step. Substitute the hypothesis into Lecture 7's recurrence. The \(k=0\) and \(k=1\) terms are degenerate (\(0\log0\) and \(1\log1\) both vanish or are handled as constants), so fold them into the \(\Theta(n)\) term and start the sum from \(k=2\):

$$E[T(n)] = \frac2n\sum_{k=2}^{n-1}k\log k+\Theta(n)$$

The key trick: convert the discrete sum into a continuous integral. Let \(f(x)=x\log x\) — an increasing function for \(x\) large. Since \(f\) is increasing, each rectangle of height \(f(k)\) and width 1 sits entirely below the curve \(f(x)\) on that same interval, so the sum of rectangle areas is bounded above by the area under the curve:

$$\sum_{k=m}^{n-1}f(k) \;\le\; \int_m^n f(x)\,dx$$

Apply this with \(m=2\):

$$E[T(n)] \le \frac{2c}n\int_2^n x\log x\,dx+\Theta(n)$$

Evaluate the integral by parts (\(u=\log x\), \(dv=x\,dx\), so \(du=\frac1x dx\), \(v=\frac{x^2}2\)):

$$\int x\log x\,dx = \log x\cdot\frac{x^2}2-\int\frac1x\cdot\frac{x^2}2\,dx = \frac{x^2}2\log x-\frac{x^2}4$$

Evaluating from 2 to \(n\):

$$\int_2^n x\log x\,dx = \left(\frac{n^2}2\log n-\frac{n^2}4\right)-\Big(2\log2-1\Big)$$

The subtracted constant \(2\log2-1\) is positive, and it's being subtracted, so dropping it can only make the bound larger — safe to discard for an upper bound:

$$\le \frac{n^2}2\log n-\frac{n^2}4$$

Substituting back:

$$E[T(n)] \le \frac{2c}n\left[\frac{n^2}2\log n-\frac{n^2}4\right]+\Theta(n) = cn\log n-\frac{cn}2+\Theta(n) = cn\log n+\left(\Theta(n)-\frac{cn}2\right)$$

Final move: choose \(c\) large enough that \(\dfrac{cn}2\) dominates the \(\Theta(n)\) term — i.e. large enough that \(\Theta(n)-\dfrac{cn}2\) is negative. Then:

$$E[T(n)] \le cn\log n$$

∎  completing the induction.

Key result

$$E[T(n)] \in O(n\log n)$$

Randomized/average-case Quicksort matches Merge Sort's speed — its notorious \(\Theta(n^2)\) worst case is genuinely a worst case, not typical behaviour.

8.2 · The decision-tree lower bound: no comparison sort beats n log n

Recall Lecture 5's puzzle: model any comparison-based sorting algorithm as a decision tree, where every internal node is a single comparison, and every leaf is a fully-determined sorted output.

Result (to be proved)

Any decision tree sorting \(n\) elements has height \(\Omega(n\log n)\) — equivalently, any comparison sort algorithm requires \(\Omega(n\log n)\) comparisons in the worst case.

Concrete illustration — sorting 3 elements

Take \(\{a_1,a_2,a_3\}\) with, say, values 9, 11, 21. There are \(3!=6\) possible orderings (permutations): \(a_1a_2a_3\), \(a_1a_3a_2\), \(a_2a_1a_3\), \(a_2a_3a_1\), \(a_3a_1a_2\), \(a_3a_2a_1\) — and each one must appear as a leaf somewhere in the decision tree, since the algorithm needs to be able to correctly output every possible sorted arrangement, depending on the input.

Every comparison-based algorithm you've studied — Bubble Sort, Selection Sort, Merge Sort, Quicksort — "basically follows the framework given by this decision-tree model," whether or not it's drawn out explicitly.

Proof

Step 1 — connect worst case to tree height. The worst-case running time of any comparison sort equals the longest path from root to leaf in its decision tree — i.e. the height of the tree, \(h\).

Step 2 — count the leaves needed. The tree's height must be large enough to accommodate every possible outcome — there must be at least \(n!\) leaves (one per permutation of the input). A binary tree of height \(h\) has at most \(2^h\) leaves (if some of that capacity is unused, imagine padding the remaining leaf slots with dummy outcomes — the capacity bound \(2^h\) still applies regardless). So:

$$2^h \ge n!$$

Step 3 — solve for \(h\). Take logs (log is monotonic, preserving the inequality):

$$h \ge \log(n!)$$

Step 4 — bound \(\log(n!)\) from below, reusing the exact technique from Lectures 2–3 (dropping the smaller half of the factors in \(n!\), keeping only the \(n/2\) largest, each \(\ge n/2\)):

$$n! \ge \Big(\frac n2\Big)\Big(\frac n2+1\Big)\cdots n \ge \Big(\frac n2\Big)^{n/2} \quad\Longrightarrow\quad \log(n!)\ge\frac n2\log\frac n2$$

And exactly as in Lecture 3's proof, splitting and bounding the threshold term shows this is \(\Omega(n\log n)\):

$$\frac n2\log\frac n2 = \frac n4\log n+\left(\frac n4\log n-\frac n2\log2\right) \ge \frac n4\log n \quad\text{for } n\ge4$$

So \(\log(n!)\in\Omega(n\log n)\) — this is literally the same result as Lecture 3's \(\log(n!)\in\Theta(n\log n)\), just reused here for a new purpose.

Conclusion:

$$h \ge \log(n!) \in \Omega(n\log n)$$

∎

The headline result

Any decision tree sorting \(n\) elements has height \(\Omega(n\log n)\) — equivalently, any comparison sort algorithm requires \(\Omega(n\log n)\) comparisons in the worst case.

Why this is the capstone of the entire sorting unit

Since Quicksort, Merge Sort, Insertion Sort, Bubble Sort, and every other algorithm covered so far all work by comparing elements, their minimum possible running time is bounded below by \(n\log n\) — no comparison-based algorithm, however cleverly designed, could ever beat this. Combined with Lecture 5's and Lecture 8's upper bounds — Merge Sort's \(\Theta(n\log n)\) worst case, and randomized Quicksort's \(\Theta(n\log n)\) average case — this proves that Merge Sort and randomized Quicksort are asymptotically optimal: we have matching upper and lower bounds, both \(\Theta(n\log n)\), so no comparison sort can ever fundamentally beat them.

So how could anything possibly sort faster than n log n?

This lower bound applies only to comparison-based algorithms — ones whose only source of information is "is this element bigger or smaller than that one?" It says nothing about algorithms that exploit extra structure in the input (for instance, knowing the elements are integers within some limited range). That escape hatch is exactly where Lecture 9 goes next: sorting in linear time, without comparisons.

Lecture 9

Sorting in Linear Time — Without Comparisons

Lecture 8 proved comparison-based sorting can never beat \(\Omega(n\log n)\). This lecture finds the escape hatch: if you're willing to exploit some extra structure in the input — instead of only asking "which is bigger?" — you can sort in genuinely linear time. Counting Sort and Radix Sort are the first two such algorithms.

9.1 · Two ways to overcome the Ω(n log n) barrier

Recall

Any comparison sort will take \(\Omega(n\log n)\) time — a genuine lower bound.

Overcoming strategies
  1. Do not use comparison — extract information about elements some other way.
  2. Put some conditions on the input — the algorithm only needs to work correctly under a reasonable assumption about what the data looks like.

Counting Sort

Setup

Input: \(A[1,\dots,n]\), where every \(A[i]\in\{1,\dots,k\}\) for some \(k\in\mathbb{N}\) — i.e. the elements are integers within a known, limited range. Output: \(B[1,\dots,n]\), sorted. Auxiliary storage: \(C[0,\dots,k]\).

1  for i ← 0 to k
2      C[i] ← 0                              // Θ(k)
3  for j ← 1 to n
4      C[A[j]] ← C[A[j]] + 1                 // Θ(n) — tally each value's frequency
5  for i ← 1 to k
6      C[i] ← C[i] + C[i-1]                  // Θ(k) — running (cumulative) total
7  for j ← n downto 1
8      B[C[A[j]]] ← A[j]                     // Θ(n) — place each element in its final slot
9      C[A[j]] ← C[A[j]] - 1
Worked example

\(A=[7_a,2_a,5_a,7_b,2_b,2_c,5_b]\) (\(n=7\), \(k=7\)) — subscripts just track each element's original position, to make stability visible.

Step 1 & 2 — frequency count (line 4): value 2 occurs 3 times, value 5 occurs twice, value 7 occurs twice, everything else 0.

i01234567
C[i]00300202

Step 3 — cumulative distribution (line 6): running total, so \(C[i]\) now tells us the index a value \(i\) should be placed up to:

i01234567
C[i]00333557

Notice \(C[7]=7=n\) — a useful sanity check, since all \(n\) elements must be accounted for by the last value.

Step 4 — place each element (lines 7–9), scanning \(A\) from the end (this is what preserves stability — placing later-appearing equal elements first would break it):

B = [2a, 2b, 2c, 5a, 5b, 7a, 7b]

Sorted — and every group of equal values keeps its original relative order (\(2_a\) before \(2_b\) before \(2_c\); \(5_a\) before \(5_b\); \(7_a\) before \(7_b\)).

Note — stability

The order of repeated numbers in the input is maintained in the output by Counting Sort. Such a sort is called a stable sort.

Analysis

$$T(n) = \Theta(k)+\Theta(n)+\Theta(k)+\Theta(n) = \Theta(n+k)$$

∎  The algorithm takes \(\Theta(n+k)\) time — genuinely linear whenever \(k\in O(n)\) (the range of values isn't too much bigger than the array itself).

9.2 · Radix Sort

Counting Sort needs \(k\) to be small. What if the numbers can be large — say, arbitrary integers — but still have a fixed number of digits? Radix Sort's idea: apply a stable sort (Counting Sort will do nicely) one digit position at a time, starting from the least significant digit.

Worked example

Sort the 3-digit numbers \(941, 176, 257, 146, 478, 972, 110\) (7 numbers, so 3 passes — one per digit column).

Pass 1 — stable-sort by the units digit (rightmost):

110, 941, 972, 176, 146, 257, 478

(units digits, in this order: 0, 1, 2, 6, 6, 7, 8 — note 176 comes before 146 among the two "6"s, preserving their original relative order from the input.)

Pass 2 — stable-sort the result of Pass 1 by the tens digit:

110, 941, 146, 257, 972, 176, 478

(tens digits: 1, 4, 4, 5, 7, 7, 7 — again, ties preserve their order from Pass 1.)

Pass 3 — stable-sort the result of Pass 2 by the hundreds digit:

110, 146, 176, 257, 478, 941, 972

Fully sorted, after exactly 3 passes.

Common confusion — why start from the least significant digit?

Sorting by the most significant digit first would seem more natural, but it doesn't work cleanly with a simple repeated stable sort — you'd need to recursively re-sort within each group. Sorting from the least significant digit first works because stability guarantees that once you sort by a more significant digit, ties are automatically broken correctly by whatever order the less-significant-digit sort already established. This is the entire reason Radix Sort needs a stable sort as its subroutine at each pass.

Lecture 10

Radix Sort, Generalized — and Pushed All the Way to Linear Time

Lecture 9 sorted decimal digits one column at a time. This lecture generalizes the idea to any base — including binary — and then asks the natural optimization question: given a fixed number of bits per number, what's the best possible digit-group size to sort with? The answer, chosen correctly, makes Radix Sort run in genuinely linear time.

10.1 · When Counting Sort alone isn't enough

Recall, and a weak spot

Counting Sort takes \(\Theta(n+k)\) time — linear only when \(k\in O(n)\). But consider \(A=[5,2,10^{10}]\): here \(n=3\), yet \(k=10^{10}\gg n^2=9\). Counting Sort would need an auxiliary array of size \(10^{10}\) — hugely wasteful. This is exactly the situation Radix Sort is built for: numbers that are large in value, but still made of a bounded number of digits.

Radix Sort — the abstract algorithm

Input: array \(A\), number of digits \(d\).

1  RadixSort(A, d)
2      for i ← 1 to d
3          do use a stable sort to sort array A on digit i

Written abstractly — any stable sort can fill the role (Counting Sort is the natural choice, as in Lecture 9).

Result 1

Given \(n\)-digit numbers in which each digit can take \(k\) possible values, Radix Sort sorts these numbers in \(\Theta(d(n+k))\) time.

Proof

A good stable sort (e.g. Counting Sort) takes \(\Theta(n+k)\) time to process every column (every digit position). There are \(d\) passes (one per column). Multiplying:

$$\Theta(d(n+k))$$

∎

Worked example — sorting in a different base entirely

Radix Sort works in any base, not just base-10 — including binary. Given 9-bit binary numbers, group each into 3-bit chunks and read them as octal digits (base 8): e.g. \(001100010\) becomes \(1\,4\,2\) in octal. Radix-sort the octal representations digit by digit (this is a smaller, more manageable digit-alphabet than sorting bit-by-bit would be), then convert back to binary once fully sorted. This flexibility — choosing how many bits to group into one "digit" — is exactly what the rest of this lecture optimizes.

10.2 · Choosing the digit size optimally

Suppose every number in the array is a fixed-width \(b\)-bit integer, and we choose to group bits into digits of \(r\) bits each. Two quantities depend on \(r\):

  • Number of passes: \(d=\left\lceil\dfrac br\right\rceil\) (total bits, divided into groups of size \(r\)).
  • Range per digit: with \(r\) bits, the largest representable digit is \(k=2^r-1\in\Theta(2^r)\) (a geometric series: \(2^{r-1}+2^{r-2}+\cdots+2^0=2^r-1\)).
Result 2

Given \(n\) \(b\)-bit numbers and any positive integer \(r\le b\), Radix Sort sorts these numbers in

$$\Theta\!\left(\left\lceil\frac br\right\rceil(n+2^r)\right)\text{ time.}$$

Proof

Directly from Result 1, substituting \(d=\lceil b/r\rceil\) and \(k=2^r-1\in\Theta(2^r)\):

$$\Theta(d(n+k)) = \Theta\!\left(\left\lceil\frac br\right\rceil(n+2^r-1)\right) = \Theta\!\left(\left\lceil\frac br\right\rceil(n+2^r)\right)$$

∎

Now — which r makes this fastest?

Choosing r to achieve Θ(n)

Aim: choose \(r\) so that \(\Theta\!\left(\dfrac br(n+2^r)\right)\in\Theta(n)\) — i.e. make the \((n+2^r)\) factor itself no bigger than \(\Theta(n)\):

$$n+2^r\in\Theta(n) \;\Longleftrightarrow\; 2^r\le n \;\Longleftrightarrow\; r=\lceil\log_2n\rceil$$

Substitute this choice of \(r\) back into Result 2 (using \(2^{\log_2n}=n\)):

$$\Theta\!\left(\frac{b}{\log_2n}\big(n+2^{\log_2n}\big)\right) = \Theta\!\left(\frac{b}{\log_2n}(n+n)\right) = \Theta\!\left(\frac{b}{\log_2n}\cdot n\right)$$

This collapses all the way to \(\Theta(n)\) whenever \(\dfrac{b}{\log_2n}\in\Theta(1)\) — i.e. whenever the bit-width \(b\) is itself proportional to \(\log n\), which is the ordinary, realistic case (an array of \(n\) distinct integers naturally needs on the order of \(\log n\) bits to represent each index/value distinctly).

$$\boxed{T(n)\in\Theta(n)} \quad\text{— genuinely linear-time sorting.}$$

∎

Worked numeric check

\(n=10\), \(b=9\) bits. Choose \(r=\lfloor\log_2 10\rfloor=3\) (a "good choice," since \(2^3=8\) is close to \(n=10\)). Then \(\dfrac{b}{\log_2n}=\dfrac{9}{\log_2 10}\le\dfrac93=3\in\Theta(1)\) — bounded by a small constant, confirming the linear-time regime.

Making this precise — two cases for how b compares to log n

Case 1: \(b<\log_2n\) (the number of bits is small). Here, simply take \(r=b\) — use all the bits as a single digit, needing just one pass (\(d=b/r=1\)):

$$T(n) = \Theta\!\left(\frac bb(n+2^b)\right) = \Theta(n+2^b)$$

Since \(b<\log_2n\), we get \(2^b<2^{\log_2n}=n\) — so the \(2^b\) term is dominated by \(n\), giving \(T(n)=\Theta(n)\). Linear, in a single pass.

Case 2: \(b\ge\log_2n\) (the more typical case for arrays of \(n\) distinct values). Here, take \(r=\log_2n\) as derived above, giving \(T(n)=\Theta(n)\) whenever \(\dfrac{b}{\log_2n}\in\Theta(1)\) — exactly the derivation just shown.

Either way, a good choice of \(r\) reaches linear time.

Where Lecture 10 leaves us

With the right choice of digit size, Radix Sort achieves genuinely linear \(\Theta(n)\) time — beating the \(\Omega(n\log n)\) comparison-sort barrier entirely, exactly as promised at the start of Lecture 9, by simply refusing to play the comparison game at all.

Lecture 11

Insertion Sort, and Bucket Sort's Beautiful Average Case

This lecture introduces one more familiar sort — Insertion Sort, the "sorting a hand of playing cards" algorithm — and then returns to the linear-time theme with Bucket Sort, whose average-case analysis is one of the most satisfying probability arguments in the whole course.

11.1 · Insertion Sort

The card-game analogy

Imagine sorting a hand of playing cards by picking them up one at a time. At every moment, the cards already in your hand are sorted; you take the next card from the table and slide it into its correct position among the cards you're already holding.

Insertion Sort — pseudocode 
1  for j ← 2 to n
2      key ← A[j]
3      i ← j-1
4      while i > 0 and A[i] > key
5          A[i+1] ← A[i]
6          i ← i-1
7      A[i+1] ← key

The already-sorted portion is \(A[1,\dots,j-1]\); each iteration picks up \(A[j]\) as the "key" card and shifts every larger element in the sorted portion one step right, opening a gap for the key to drop into.

Worked example

\(A=[5,4,1,10,2,18]\):

jkeyArray after this pass
244, 5, 1, 10, 2, 18
311, 4, 5, 10, 2, 18
4101, 4, 5, 10, 2, 18  (already in place)
521, 2, 4, 5, 10, 18
6181, 2, 4, 5, 10, 18  (already in place)

Final: fully sorted in 5 passes (\(n-1\)).

Worst-case analysis

Worst case: the array is in descending order, so every element must shift all the way past everything already placed. This is a double sum, exactly like Bubble Sort and Selection Sort's:

$$T(n) = \sum_{j=2}^{n}\sum_{i=j-1}^{n-1}1 = \sum_{j=2}^{n}\big(n-1-(j-1)+1\big) = \sum_{j=2}^n(n-j+1)$$

$$= (n-1)+(n-2)+\cdots+1 = \frac{(n-1)n}2 \in \Theta(n^2)$$

∎  Since the worst-case time complexity of Insertion Sort is \(\Theta(n^2)\), Bucket Sort — which uses Insertion Sort as a subroutine — inherits this same worst case, as the next section shows.

A tangent — the Collatz conjecture

The lecture takes a fun detour into an unrelated but famous open problem: pick any positive integer \(n\). If it's even, halve it; if it's odd, compute \(3n+1\). Repeat. The conjecture ("\(3n+1\) conjecture," or Collatz conjecture) is that this process always eventually reaches 1, no matter which number you start with — e.g. \(19\to58\to29\to88\to44\to22\to11\to34\to17\to52\to26\to13\to40\to20\to10\to5\to16\to8\to4\to2\to1\), and \(74\to37\to\cdots\to1\). Despite being trivial to state, nobody has ever proven it true for every starting number.

11.2 · Bucket Sort

Assumption

The elements are uniformly distributed over \([0,1)\).

Bucket Sort — pseudocode 
1  BucketSort(A)
2      n ← length(A)
3      for j ← 1 to n
4          do insert A[j] into auxiliary array B of linked lists, at B[⌊nA[j]⌋]
5      for i ← 0 to n-1
6          do sort list B[i] with Insertion Sort
7      concatenate the lists B[0], B[1], …, B[n-1], in order

The idea: split \([0,1)\) into \(n\) equal-width "buckets," toss every element into the bucket its value falls into, sort each (small) bucket individually, then read the buckets off in order.

Worked example

\(A=[0.1,\,0.72,\,0.5,\,0.3,\,0.01,\,0.75,\,0.35,\,0.78,\,0.6,\,0.9]\) (\(n=10\)). Bucket \(i\) covers \(\left[\frac{i}{10},\frac{i+1}{10}\right)\):

B[6][0.6, 0.7)0.6
B[7][0.7, 0.8)0.72, 0.75, 0.78

Concatenating: \(0.01,\,0.1,\,0.3,\,0.35,\,0.5,\,0.6,\,0.72,\,0.75,\,0.78,\,0.9\) — sorted.

Note — the uniform-distribution assumption is essential

If the input isn't uniformly distributed, elements can pile up into one or a few buckets, and Bucket Sort degrades toward the worst case of whatever sort runs inside each bucket (Insertion Sort). E.g. if every element lands in bucket \([0.7,0.8)\), that one bucket alone does all the work.

Worst-case analysis

Worst case: all \(n\) numbers fall inside a single bucket — then that bucket's Insertion Sort call does all the work, and since Insertion Sort's worst case is \(\Theta(n^2)\):

$$\text{Bucket Sort's worst case} \in \Theta(n^2)$$

∎

Lecture 12

Bucket Sort's Average Case, and Fast Integer Multiplication

This lecture finishes the rigorous probability argument for Bucket Sort — proving it's linear on average — then completely changes gears: multiplying two large numbers, and Karatsuba's surprising trick for doing it faster than the method you learned in school.

12.1 · Bucket Sort's average case, completed

Setup, recalled from Lecture 11

\(X_{ij}=1\) if \(A[j]\) falls in bucket \(B[i]\), else \(0\). Then \(n_i=\displaystyle\sum_{j=1}^nX_{ij}\) is the number of elements landing in bucket \(i\), and since each bucket is sorted with Insertion Sort:

$$T(n) = \sum_{i=0}^{n-1}O(n_i^2)+\Theta(n)$$

Proof — finding \(E[n_i^2]\)

Expand \(n_i^2\) as a squared sum, splitting into "matching" terms (\(j=k\)) and "cross" terms (\(j\ne k\)):

$$E[n_i^2] = E\left[\left(\sum_{j=1}^nX_{ij}\right)^2\right] = E\left[\sum_{j=1}^nX_{ij}^2+\sum_{j=1}^n\sum_{\substack{k=1\\k\ne j}}^nX_{ij}X_{ik}\right] = \sum_{j=1}^nE[X_{ij}^2]+\sum_{j=1}^n\sum_{\substack{k=1\\k\ne j}}^nE[X_{ij}]E[X_{ik}]$$

(the cross terms factor as \(E[X_{ij}]E[X_{ik}]\) because different array elements land in their buckets independently of one another)

Since \(X_{ij}\) only ever takes values \(0\) or \(1\), \(X_{ij}^2=X_{ij}\), so \(E[X_{ij}^2]=E[X_{ij}]\). And under the uniform-distribution assumption, each element has probability exactly \(\frac1n\) of landing in any particular bucket, so \(E[X_{ij}]=\frac1n\) for every \(i,j\). Substituting:

$$E[n_i^2] = \sum_{j=1}^n\frac1n+\sum_{j=1}^n\sum_{\substack{k=1\\k\ne j}}^n\frac1n\cdot\frac1n = \frac1n(n)+\frac1{n^2}\big(n^2-n\big)$$

(there are \(n^2-n\) ordered pairs \((j,k)\) with \(j\ne k\), out of \(n^2\) total pairs)

$$= 1+\frac{n(n-1)}{n^2} = 1+1-\frac1n = 2-\frac1n$$

$$\boxed{E[n_i^2] = 2-\frac1n}$$

∎

Proof — substituting back to find \(E[T(n)]\)

$$E[T(n)] = \sum_{i=1}^nO\Big(2-\frac1n\Big)+\Theta(n) = n\cdot O\Big(2-\frac1n\Big)+\Theta(n)$$

Since \(2\) is a constant and \(0<\frac1n<1\), the quantity \(2-\frac1n\) is itself bounded by a constant, so \(n\cdot O\big(2-\tfrac1n\big)\in O(n)\) — this term is small compared to the \(\Theta(n)\) concatenation cost, which dominates:

$$E[T(n)] \in \Theta(n)$$

∎  Hence, Bucket Sort runs in \(\Theta(n)\) time on average.

12.3 · Karatsuba's Algorithm — multiplying large numbers faster

The naive method

Multiplying two \(n\)-digit numbers by hand (the method taught in school) needs \(n\) multiplications for each digit of the second number against the first — \(n\times n=n^2\) single-digit multiplications in total.

Worked example — the naive method

\(34\times21\): \(34\times1=34\), \(34\times2=68\) (shifted one place), sum \(34+680=714\). Two 2-digit numbers → \(2\times2=4\) single-digit multiplications, plus one addition.

The idea — do it with only 3 multiplications

For 2-digit numbers, write \(34=3\times10+4\) and \(21=2\times10+1\). Naively, \((3\times10+4)(2\times10+1)\) needs 4 multiplications (\(3\times2\), \(3\times1\), \(4\times2\), \(4\times1\)). Karatsuba's trick: compute \((3+4)(2+1)=7\times3=21\) — one extra multiplication that, combined with just two of the four originally needed products, recovers everything:

$$(a+b)(c+d) = ac+ad+bc+bd \quad\Longrightarrow\quad ad+bc = (a+b)(c+d)-ac-bd$$

So if you've already computed \(ac\) and \(bd\) separately, the middle term \(ad+bc\) can be recovered from just one more multiplication, \((a+b)(c+d)\), instead of two (\(ad\) and \(bc\) separately) — 3 multiplications total instead of 4.

Karatsuba's algorithm, set up in general

To multiply \(a\times b\), split each number in half (by digit count), with \(n/2\) digits per half:

$$a = a_1\cdot10^{n/2}+a_0, \qquad b = b_1\cdot10^{n/2}+b_0$$

$$a\times b = (a_1\cdot10^{n/2}+a_0)(b_1\cdot10^{n/2}+b_0) = a_1b_1\cdot10^n+(a_1b_0+a_0b_1)\cdot10^{n/2}+a_0b_0$$

Write \(c=a\times b=c_2\cdot10^n+c_1\cdot10^{n/2}+c_0\), where:

$$c_2=a_1b_1, \qquad c_0=a_0b_0, \qquad c_1=(a_1+a_0)(b_1+b_0)-c_2-c_0$$

Only 3 multiplications are needed: \(a_1b_1\), \(a_0b_0\), and \((a_1+a_0)(b_1+b_0)\) — never \(a_1b_0\) or \(a_0b_1\) individually.

Worked example — \(345\times217\)

Pad to an even digit count if needed (here already 3 digits each is fine conceptually, but pad the split evenly: \(n=4\), treating as \(0345\times0217\)): \(a_1=03,\,a_0=45,\,b_1=02,\,b_0=17\).

$$c_2 = a_1b_1 = 03\times02 = 6$$

$$c_0 = a_0b_0 = 45\times17 = 765$$

$$c_1 = (a_1+a_0)(b_1+b_0)-c_2-c_0 = (48)(19)-6-765 = 912-6-765 = 141$$

$$c = c_2\cdot10^4+c_1\cdot10^2+c_0 = 6\times10^4+141\times10^2+765 = 60000+14100+765 = 74865$$

Check against direct multiplication: \(345\times217=74865\)

Match confirmed.
A smaller worked example, for extra intuition — 34 × 21

\(a=34\): \(a_1=3,\,a_0=4\). \(b=21\): \(b_1=2,\,b_0=1\).

$$c_2=a_1b_1=3\times2=6, \qquad c_0=a_0b_0=4\times1=4$$

$$c_1=(a_1+a_0)(b_1+b_0)-c_2-c_0=(7)(3)-6-4=21-10=11$$

$$c = c_2\cdot10^2+c_1\cdot10+c_0 = 600+110+4 = 714$$

Check: \(34\times21=714\).  Match confirmed — and notice this is exactly the "3 multiplications instead of 4" trick from the introduction, now expressed in the algorithm's general notation.

Where Lecture 12 leaves us

Karatsuba's algorithm replaces one \(n\)-digit multiplication with three \((n/2)\)-digit multiplications, plus some cheap additions — a genuine divide-and-conquer algorithm. Its time complexity, and whether 3 recursive calls of half the size actually beats the naive \(\Theta(n^2)\), is exactly where Lecture 13 begins.

Lecture 13

Karatsuba's Complexity, and Strassen's Matrix Multiplication

The final lecture of this collection finishes what Lecture 12 started — proving Karatsuba's algorithm is genuinely faster than the schoolbook method — and then applies the exact same "fewer multiplications, more additions" idea to a completely different problem: multiplying matrices.

13.1 · Karatsuba's time complexity

Setting the baseline

Brute-force multiplication takes \(\Theta(n^2)\) time for \(n\)-digit multiplicands. Even the "obvious" divide-and-conquer approach — split each number in half and do 4 separate half-size multiplications (\(a_1b_1\), \(a_1b_0\), \(a_0b_1\), \(a_0b_0\)) — doesn't actually help:

Proof — the "obvious" 4-multiplication approach gains nothing

$$T(n) = 4T\Big(\frac n2\Big)$$

Unrolling: \(T(n)=4^kT(n/2^k)\), and with \(2^k=n\) (so \(k=\log_2n\)) and \(T(1)=1\):

$$T(n) = 4^{\log_2n} = \big(2^{\log_2n}\big)^2 = n^2 \in \Theta(n^2)$$

∎  — exactly matching brute force. Splitting the problem alone doesn't help; you need to actually reduce the number of multiplications.

Proof — Karatsuba's 3-multiplication recurrence, solved

$$T(n) = 3T\Big(\frac n2\Big)$$

Unrolling exactly as before: \(T(n)=3^kT(n/2^k)\), with \(2^k=n\), \(T(1)=1\):

$$T(n) = 3^{\log_2n}$$

To express this as a power of \(n\), write \(3^{\log_2n}=n^x\) and solve for \(x\) by taking \(\log_3\) of both sides:

$$\log_3\big(3^{\log_2n}\big) = \log_3(n^x) \;\Longrightarrow\; \log_2n\cdot\log_33 = x\log_3n \;\Longrightarrow\; \log_2n = x\log_3n$$

$$\Longrightarrow\; x = \frac{\log_2n}{\log_3n}$$

Converting both logs to a common base (natural log) and simplifying via the change-of-base formula:

$$x = \frac{\log_en/\log_e2}{\log_en/\log_e3} = \frac{\log_e3}{\log_e2} = \log_23 \approx 1.58$$

Key result

$$T(n) \in \Theta\big(n^{\log_23}\big) = \Theta(n^{1.585\ldots})$$

∎

Why this matters

\(n^{1.585}\) is genuinely smaller than \(n^2\) for large \(n\) — Karatsuba's algorithm really is asymptotically faster than the schoolbook method, purely by trading one multiplication for a few extra additions at every level of recursion. This is the same "reduce the branching factor of the recursion" idea that will now be applied to matrix multiplication.

13.2 · Strassen's Matrix Multiplication

The baseline — ordinary 2×2 matrix multiplication

$$\begin{bmatrix}a_{00}&a_{01}\\a_{10}&a_{11}\end{bmatrix}\begin{bmatrix}b_{00}&b_{01}\\b_{10}&b_{11}\end{bmatrix} = \begin{bmatrix}a_{00}b_{00}+a_{01}b_{10} & a_{00}b_{01}+a_{01}b_{11}\\a_{10}b_{00}+a_{11}b_{10} & a_{10}b_{01}+a_{11}b_{11}\end{bmatrix}$$

Each of the 4 output entries needs 2 multiplications: \(2\times4=8\) multiplications in total, the brute-force way.

Proof — brute-force matrix multiplication is Θ(n³)

Recursively, splitting an \(n\times n\) matrix product into four \((n/2)\times(n/2)\) quadrant-products, each needing 2 sub-multiplications: \(T(n)=8T(n/2)\). Unrolling exactly as before (\(2^k=n\), \(T(1)=1\)):

$$T(n) = 8^{\log_2n} = \big(2^{\log_2n}\big)^3 = n^3 \in \Theta(n^3)$$

∎  The usual (brute-force) matrix multiplication time complexity is \(\Theta(n^3)\).

Strassen's trick — the same product, using only 7 multiplications

Define seven products:

$$m_1=(a_{00}+a_{11})(b_{00}+b_{11}) \qquad m_2=(a_{10}+a_{11})b_{00} \qquad m_3=a_{00}(b_{01}-b_{11})$$

$$m_4=a_{11}(b_{10}-b_{00}) \qquad m_5=(a_{00}+a_{01})b_{11} \qquad m_6=(a_{10}-a_{00})(b_{00}+b_{01})$$

$$m_7=(a_{01}-a_{11})(b_{10}+b_{11})$$

Then the product matrix is recovered entirely from additions and subtractions of these seven values:

$$C = \begin{bmatrix}m_1+m_4-m_5+m_7 & m_3+m_5\\m_2+m_4 & m_1+m_3-m_2+m_6\end{bmatrix}$$

Verifying this is correct — the homework, completed

The lecture verifies one entry and leaves the rest as an exercise. Here, all four are checked against the brute-force formula above.

Entry (1,2): \(m_3+m_5 = a_{00}b_{01}-a_{00}b_{11}+a_{00}b_{11}+a_{01}b_{11} = a_{00}b_{01}+a_{01}b_{11}\) ✓  (matches directly)

Entry (2,1): \(m_2+m_4 = a_{10}b_{00}+a_{11}b_{00}+a_{11}b_{10}-a_{11}b_{00} = a_{10}b_{00}+a_{11}b_{10}\) ✓

Entry (1,1): expand \(m_1+m_4-m_5+m_7\) fully and collect like terms — every term cancels except \(a_{00}b_{00}\) and \(a_{01}b_{10}\):

$$m_1+m_4-m_5+m_7 = a_{00}b_{00}+\cancel{a_{00}b_{11}}+\cancel{a_{11}b_{00}}+\cancel{a_{11}b_{11}}+\cancel{a_{11}b_{10}}-\cancel{a_{11}b_{00}}-\cancel{a_{00}b_{11}}-a_{01}b_{11}+a_{01}b_{10}+a_{01}b_{11}-\cancel{a_{11}b_{10}}-\cancel{a_{11}b_{11}}$$

$$= a_{00}b_{00}+a_{01}b_{10} \quad\checkmark$$

Entry (2,2): expand \(m_1+m_3-m_2+m_6\) the same way — everything cancels except \(a_{11}b_{11}\) and \(a_{10}b_{01}\):

$$m_1+m_3-m_2+m_6 = a_{11}b_{11}+a_{10}b_{01} \quad\checkmark$$

∎  All four entries match brute-force multiplication exactly — Strassen's algorithm is correct, and it needed only 7 multiplications, not 8.

Proof — Strassen's time complexity

$$T(n) = 7T\Big(\frac n2\Big)$$

Following the identical method used for Karatsuba: unroll to \(T(n)=7^{\log_2n}\), write \(7^{\log_2n}=n^x\), and solve by taking \(\log_7\) of both sides:

$$\log_2n = x\log_7n \;\Longrightarrow\; x = \frac{\log_2n}{\log_7n} = \log_27$$

Key result

$$T(n) \in \Theta\big(n^{\log_27}\big) = \Theta(n^{2.807\ldots})$$

∎

Where this course's uploaded material ends

Strassen's algorithm beats brute-force matrix multiplication's \(\Theta(n^3)\) with \(\Theta(n^{2.807})\) — the exact same "buy a few extra additions, save a multiplication" trade that made Karatsuba's algorithm faster than the schoolbook method. Both results are genuinely surprising the first time you see them: multiplication, which feels like the "expensive" primitive operation, turns out to be the very thing worth economizing on, even at the cost of noticeably messier bookkeeping.

Full Course Recap

Thirteen lectures, one continuous story: every algorithm in this collection is an answer to the same recurring question — "the obvious way works, but can we prove something better is possible, and then actually build it?" Here's how it all connects.

Techniques that kept reappearing

  • Unrolling a recurrence by hand until a pattern emerges, then solving via a geometric series or by matching \(n^x\) to a power — used for Tower of Hanoi, Merge Sort, Quicksort, Karatsuba, and Strassen alike.
  • The recursion-tree method — draw the recursion, notice every level sums to the same total, multiply by the height.
  • The limit-comparison test — the single tool used to compare literally any two growth rates in this course.
  • Bounding a discrete sum by a continuous integral — the trick that finished both the \(\log(n!)\) proof and Quicksort's average-case proof.
  • Indicator random variables — turning "did this random event happen?" into a 0/1 variable you can take the expectation of, used identically for Quicksort and Bucket Sort.
  • Proof by contradiction against an adversarially-constructed input — the technique behind both the max-finding lower bound (Lecture 3) and the sorting lower bound (Lecture 8).

Mini glossary

AlgorithmA sequence of well-defined operations, taking an input, processing it, to give an output, in finite time.
\(O(g(n))\), \(\Omega(g(n))\), \(\Theta(g(n))\)Bounded above by, bounded below by, and bounded both ways by (i.e. same growth rate as) \(g(n)\), up to a constant factor.
Recurrence relationAn equation defining \(T(n)\) in terms of \(T\) at smaller inputs — the standard way to describe a divide-and-conquer algorithm's running time.
Stable sortA sort that preserves the original relative order of equal elements.
Decision tree modelModelling a comparison-based algorithm as a binary tree, where each internal node is one comparison and each leaf is one possible final answer.
Indicator random variableA variable that is 1 if some event occurs and 0 otherwise — makes counting random occurrences via expectation straightforward.
Lower bound (Ω result)A proof that no algorithm (of some class) can possibly do better than a stated running time — stronger than just describing one algorithm's performance.
